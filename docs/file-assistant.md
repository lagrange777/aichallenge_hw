# Файловый ассистент: день 34

`/work <цель>` в главном чате открывает файловый режим. Можно сразу открыть `/work`, сформулировать задачу и нажать «Выполнить задачу». Модель самостоятельно выбирает файлы и порядок действий. Текст в поле — цель, не список команд для заранее заданного сценария.

## Запуск и Docker

Из корня проекта:

```sh
python3 scripts/prepare-workspace.py
# Настройте OPENAI_API_KEY в локальном .env.
docker compose up --build -d
```

Откройте http://127.0.0.1:8080/work. Скрипт создаёт `.workspaces/project`: независимую копию публичных отслеживаемых исходников и документации с локальным Git baseline. Содержимое берётся из текущего checkout, включая изменения отслеживаемых файлов. Секреты, `.env`, исходная `.git`, история пользователей и артефакты не копируются. Скрипт отказывается перезаписывать существующий каталог. Для новой копии укажите новый `--output`, затем подключите этот каталог к `/workspace` в Compose.

Compose подключает только эту копию с правом записи; корневая файловая система контейнера остаётся read-only. Подготовленная копия сохраняется на хосте после пересоздания Docker, задачи — в `/data/file-tasks` именованного тома `chat-history`. Проверить реальные изменения: `git -C .workspaces/project diff` и `git -C .workspaces/project status --short` (созданные файлы будут untracked). Исходный checkout приложения не меняется. Правки можно перенести вручную после просмотра diff.

Нативный запуск: `WORKSPACE_ROOT=/absolute/path/to/public-workspace go run ./cmd/codex-chat`. Без `WORKSPACE_ROOT` режим выключен с HTTP 503. По умолчанию запись в checkout приложения не включается.

## MCP и агент

Файловый режим использует настоящий MCP SDK: для каждой задачи создаётся сервер `codex-file-workspace`, клиент выполняет initialize, tools/list и tools/call через парные in-memory транспорты. Это отдельный канал от общего MCP чата; разрешения других подключений не расширяются, дополнительный сетевой порт не публикуется. Секрет OpenAI в инструменты не передаётся.

Инструменты:

- `list_files`: до 1500 публичных файлов.
- `search_files`: поиск литерала по нескольким файлам, максимум 60 совпадений с номерами строк, признак усечения.
- `read_file`: полный UTF-8 текст до 96 KiB, SHA-256 и признак существования.
- `propose_patch`: полное новое содержимое README.md или Markdown в docs/, максимум 8 целевых файлов; создаёт предложение без записи на диск.
- `get_diff`: общий unified diff предложений, включая новые файлы.
- `finish_task`: явное завершение с результатом ready / no_changes / blocked и фактической сводкой. Текстовое обещание модели не считается выполнением; допускаются два ограниченных напоминания, затем задача завершается ошибкой.

Модель использует существующий OpenAI Responses API клиент и функцию вызова инструментов. Для продолжений используется previous_response_id; как и в основном MCP-чате, Responses store включён. Публичные прочитанные фрагменты отправляются в OpenAI. Модель, ключ и endpoint задаются существующими OPENAI_* настройками. Автономная задача ограничена 5 минутами, 18 раундами, 30 вызовами инструментов и 10000 выходных токенов на запрос. Одновременно допускаются две задачи, одна на браузер; хранится максимум 200 задач на экземпляр.

Перед предложением изменений сервер требует чтение минимум трёх существующих файлов; существующая цель должна быть прочитана. Поиск помогает навигации, прямое чтение актуальных файлов является основанием изменений. Дополнительный RAG-индекс для этого не требуется; существующий `/help` с RAG остаётся доступен.

Запись доступна только через отдельный HTTP endpoint после нажатия «Применить изменения». Такого инструмента у модели нет. Проверяются SHA-256 всех прочитанных зависимостей и существование/содержимое целевых файлов. При конфликте нужно повторить анализ. Перед записью выполняется полный preflight; каждый файл заменяется через временный файл и rename. При обычной ошибке записи выполняется откат уже записанных файлов; сбой процесса между несколькими rename не является транзакцией всей файловой системы. Не редактируйте workspace параллельно во внешнем редакторе во время применения: блокировка координирует процессы приложения, не внешний редактор.

Пути ограничены через os.Root и allowlist; симлинки, обходы `..`, скрытые файлы, пользовательские данные, сгенерированные каталоги и выполнение команд запрещены. Исходники доступны для чтения, запись ограничена документацией. Ограничения действуют сервером, независимо от инструкции модели. Локальный веб-интерфейс не предназначен для публикации в интернет; cookie разделяет задачи браузеров, но не заменяет полноценную многопользовательскую авторизацию.

## Два сценария

1. «Проверь описание HTTP API на соответствие реализации и исправь доказанные расхождения в документации». Ассистент ищет регистрацию маршрутов и обработчики, читает исходники и документацию, готовит diff. В проверочной копии заранее задаётся известное расхождение: POST вместо GET для истории и /health вместо /healthz. Это изменение документации для проверки, не ошибка production-кода.
2. «Изучи подключение MCP и создай ADR с объяснением архитектуры, ограничений и последствий решения». Ассистент читает сервер, клиент, конфигурацию и документы, проверяет существующие ADR и создаёт документ со ссылками на исходники.

Просмотрите журнал: минимум три разных прочитанных файла, самостоятельно выбранных моделью. До применения убедитесь, что файлы не менялись. Просмотрите diff, примените и проверьте статус «Сохранено в файлы». Повторите ту же цель: если результат уже соответствует задаче, ожидается «Изменений не требуется». Повторный анализ — новые платные запросы; битовая идентичность текста модели не гарантируется.

## API и проверки

- GET `/api/work/tasks`: задачи текущего браузера.
- GET `/api/work/task?id=...`: состояние, журнал, прочитанные файлы, diff, токены и время.
- POST `/api/work/start`: `{ "goal": "цель" }`.
- POST `/api/work/apply`: `{ "id": "ID задачи" }`.

POST требует `Content-Type: application/json` и `X-File-Work: 1`, проверяются Origin и Sec-Fetch-Site. Чужие задачи недоступны. GET/POST ответы не кэшируются.

`go test -race ./internal/filework` проверяет реальный MCP transport, изоляцию путей/симлинков, отсутствие записи до применения, доступ владельца, конфликты зависимостей, сохранение/восстановление и одинаковые повторные предложения, цикл инструментов модели и HTTP-защиты. `scripts/evaluate-work.py` выполняет оба сценария и повторы через HTTP/OpenAI, сохраняет фактические ответы и проверки в artifacts/work34.
