# Цитаты, источники и анти-галлюцинации

Строгий RAG доступен во вкладке **RAG → Спросить с проверкой цитат** и в обычном чате: включить RAG; в настройках по умолчанию включена проверка утверждений и цитат. Для сравнения со старым режимом проверку можно отключить. Корпус — прежний замороженный снимок, переиндексация не требуется.

## Пайплайн

1. Поиск 20 кандидатов, оценка релевантности 0–3, порог не ниже 2, до 5 чанков в контексте. Строгий режим допускает `filter` или `full` (с query rewrite); в демонстрации используется `filter`.
2. Пустой отбор: сервер сразу отвечает «Не знаю… Уточните…», без генерации ответа. Это не означает отсутствие факта во всём корпусе, только недостаток отобранных доказательств.
3. Модель получает только текущий вопрос и пронумерованные строки отобранных источников. Возвращает JSON: `status`, `claims[]`, для каждого утверждения — `evidence[]` с `ref/start/end`. История, профиль, память и MCP не являются доказательствами и не передаются генератору/проверяющему. Правила активной задачи по-прежнему проверяются перед ответом и на окончательном тексте.
4. Сервер проверяет JSON, наличие доказательств у каждого утверждения, существование ссылок и границы строк. Цитата извлекается из исходного чанка без перефразирования. Источники в `retrieval.grounding.sources` — только использованные, с `source/title/section/chunkId`; полный набор поиска сохранён отдельно в `retrieval.sources`.
5. Отдельный LLM-вызов оценивает каждую пару «утверждение — цитаты», учитывая контекст и исходный вопрос. Ожидания из набора вопросов ему недоступны. Все утверждения должны получить `supported`; допускается одна попытка исправления с повторной проверкой. Непроверенный текст не попадает в ответ и историю.
6. `answered` — полный ответ; `partial` — подтверждённые факты и просьба уточнить недостающую часть; `unknown` — отсутствие подтверждённого ответа и просьба уточнить, пустые массивы источников/цитат. Ошибка API, некорректный проверяющий или провал исправления — HTTP-ошибка, а не «не знаю».
7. Финальный текст собирает сервер из проверенных утверждений, цитат и метаданных; после сборки нет LLM-перефразирования. Если включены инварианты, проверяется именно этот текст, нарушение блокирует сохранение.

Это снижает риск галлюцинаций, но не доказывает истинность исходных документов. Семантический проверяющий может ошибаться и использует ту же модель. Порог 2/3 — порядковая оценка релевантности, не вероятность. Наличие точной цитаты само по себе не доказывает утверждение.

## Воспроизведение

```sh
go run ./cmd/rag-grounding -env-file .env
# Продолжить прерванный прогон, сохраняя готовые ответы:
go run ./cmd/rag-grounding -env-file .env -resume
```

Это платные запросы OpenAI. Ключ не сохраняется в отчёте. Параметры: `-index`, `-questions`, `-out`, `-model`. Для нового эксперимента используйте другой `-out`. Docker содержит `/rag-grounding`; чтение отчёта настраивается `RAG_GROUNDING_PATH`.

Набор `documents/rag24-questions.json`: 7 вопросов с ожидаемыми фактами и источниками, 3 вопроса о неописанных настройках. Поиск выполняется **один раз на вопрос**: обычный и строгий RAG получают идентичные чанки. Нет истории, профиля, памяти и MCP. Итоговая оценка отдельным вызовом той же модели видит ожидания и полный ответ; это не независимый человеческий аудит.

Артефакты: `artifacts/rag24/comparison.json` (ответы, чанки, цитаты, хеши, оценки, токены), `comparison.md` (таблица и тексты). Наличие ссылок, цитат и точное совпадение проверяется кодом; смысл, корректность и полнота — моделью. Для обычного RAG распознаются явно оформленные Markdown blockquote; простые ссылки не считаются цитатами. Отказы без утверждений не требуют цитат; правильные и ложные отказы учитываются отдельно. Значения `false` для наличия цитат у отказа означают отсутствие, а не нарушение контракта.

Учёт расхода: общие поиск и reranker записаны в `pair.retrieval` один раз; `before/after.usage` содержит генерацию и проверки соответствующего ответа; `evaluationSteps` — отдельная стоимость оценки. Resume проверяет модель, хеш корпуса/набора, параметры и инструкции строгой генерации/проверки/оценки.

API: `GET /api/rag/grounding` — сохранённое сравнение; `POST /api/rag/run` — `{query, model, options:{mode:"filter",topKBefore:20,topKAfter:5,relevanceThreshold:2,grounded:true}}`. В чате тот же флаг находится в `ragOptions`. Старые API сохраняют совместимость: отсутствие `grounded` оставляет обычный RAG.

## Проверки

Unit/integration-тесты охватывают выдуманные ссылки, неверные диапазоны, отсутствие доказательств, дополнительный JSON, исправление с повторной проверкой, неполный ответ, отсутствие LLM-вызова при пустом отборе, ошибку API, запрет сохранения непроверенного ответа, изоляцию состояния, учёт токенов, HTTP-валидацию и выполнение полного API-пайплайна.

## Результат реального прогона

`gpt-5.3-codex`, 10 вопросов, отчёт завершён. Среди 7 вопросов с ответом обычный RAG дал ссылки в 7/7, но явные цитаты в 0/7; строгий режим дал источники и точные цитаты в 7/7, смысл подтверждён итоговым оценщиком в 7/7. На трёх неответимых вопросах оба режима корректно признали отсутствие информации; строгий режим во всех трёх случаях вернул `unknown` с просьбой уточнить.

Средние корректность и полнота в обоих режимах — 2/2: на этом небольшом наборе прироста фактической точности не обнаружено. Улучшение — проверяемые цитаты и принудительный контракт ответа. Генерация и проверки (без общего поиска и итогового оценивания): 12 589 → 20 284 LLM-токена, суммарно 20,4 → 30,2 секунды на 10 вопросов. Это один прогон; оценки и время могут меняться. Затраты неудавшихся API-вызовов до возобновления прогона не входят в сохранённые метрики.
