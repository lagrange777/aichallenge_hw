# Архитектура Codex Chat Web

Дата обновления: 2026-09-13.

## Цель

Однопроцессное веб-приложение на Go передаёт сообщения из локальной страницы
отдельной сущности `agent.Agent`. Агент инкапсулирует полный цикл запроса и
ответа LLM, а HTTP-клиент только взаимодействует с OpenAI Responses API.
Frontend встроен в бинарник; отдельный Node.js-процесс, сборщик или CDN не нужны.

## Компоненты

```text
cmd/codex-chat/main.go
        │
        ├── internal/config     переменные окружения и адрес HTTP-сервера
        ├── internal/web        маршруты, browser-сессии и встроенные assets
        │       └── static      HTML, CSS и JavaScript
        ├── internal/agent      агент, контекст и логика запроса/ответа
        ├── internal/history    атомарное JSON-хранилище диалогов
        ├── internal/openai     транспорт и точный подсчёт токенов Responses API
        └── internal/models     модели, контекстные лимиты и стоимость токенов

Dockerfile                     тесты, сборка и минимальный runtime-образ
compose.yaml                   запуск на http://127.0.0.1:8080
```

### `internal/web`

Отдаёт страницу и маршруты `/api/chat`, `/api/history`, `/api/reset`,
`/api/branches/create`, `/api/branches/switch`, `/api/status`, `/healthz`.
При первом сообщении создаёт случайный идентификатор и HttpOnly/SameSite cookie.
Каждому идентификатору соответствует отдельный `agent.Agent`, поэтому контекст
разных браузеров не смешивается. Неактивные экземпляры агента удаляются из
оперативной памяти через 12 часов; их JSON-история остаётся на диске и будет
загружена при следующем обращении. Одновременно в памяти хранится не более 256
сессий.

Frontend загружает отображаемый транскрипт с сервера через `/api/history`.
Выбранная модель отправляется с каждым сообщением. Под каждым новым ответом
frontend показывает метрики конкретного хода: модель, длительность, токены и
стоимость. Метрики всей беседы — активный контекст, история, накопленные токены
и стоимость — отображаются отдельно в левой панели.
До первого сообщения frontend передаёт выбранную стратегию контекста и N
последних сообщений. Агент фиксирует параметры для диалога; при загрузке
истории web-слой возвращает их вместе с facts, ветками и транскриптом.

### `internal/agent`

Принимает `agent.Request`, нормализует параметры, формирует независимый от
OpenAI `CompletionRequest`, вызывает LLM через интерфейс `agent.LLM` и собирает
`agent.Response`. Агент владеет сообщениями, `previous_response_id` и выбранной
моделью, измеряет длительность, нормализует usage и рассчитывает стоимость.
Перед генерацией агент через `agent.TokenCounter` получает число токенов
текущего запроса и полного активного контекста. Из сохранённых метрик он также
вычисляет накопленные токены и стоимость всего диалога.
После успешного ответа агент атомарно сохраняет новое состояние через интерфейс
`agent.History`. При создании агента состояние загружается обратно. При смене
модели агент передаёт новой модели сохранённый транскрипт и начинает на его
основе новую цепочку Responses API.

Агент поддерживает три summary-free стратегии. Sliding Window каждый раз
передаёт только последние N сообщений. Sticky Facts сначала обновляет отдельную
key-value память, затем передаёт developer-блок facts и последние N сообщений.
Обе стратегии намеренно не используют `previous_response_id`, иначе скрытая
серверная цепочка вернула бы отброшенную историю. Branching создаёт checkpoint,
клонирует его в две ветки и хранит для каждой собственные сообщения, модель и
`previous_response_id`. Полный локальный транскрипт, facts и все ветки
сохраняются в `ConversationState`.

### `internal/history`

Реализует `agent.History` одним JSON-файлом. В файле находятся независимые
диалоги, ключом служит случайный идентификатор из browser-cookie. Запись идёт во
временный файл с последующей атомарной заменой, чтобы аварийное завершение не
оставило частично записанный JSON. В Docker каталог `/data` подключён как
именованный том.

### `internal/openai`

Реализует интерфейс `agent.LLM` и вызывает `POST /v1/responses`, передавая
модель, инструкции, текст и `previous_response_id`. Инструкции отправляются на каждом ходу, поскольку они не
наследуются автоматически при продолжении ответа. Все блоки `output_text`
собираются в итоговую строку.
Из поля `usage` читаются входные, выходные, кэшированные и reasoning-токены.
Этот же клиент реализует `agent.TokenCounter` через
`POST /v1/responses/input_tokens`. Для продолженного диалога параллельно
считаются запрос без истории и точный запрос с `previous_response_id` либо
явно переданным транскриптом после смены модели.

### `internal/models`

Задаёт разрешённый список моделей для интерфейса и снимок публичных тарифов.
Стоимость рассчитывается на сервере отдельно для обычных, кэшированных,
записываемых в кэш и выходных токенов. Для GPT-5.6 учитываются опубликованные
коэффициенты длинного контекста после 272 000 входных токенов. Расчёт является
оценкой: тарифы могут измениться, а отдельная стоимость инструментов не входит
в результат.

Официальный контракт:
https://developers.openai.com/api/reference/cli/resources/responses/methods/create

## Поток сообщения

1. JavaScript добавляет сообщение пользователя и индикатор ожидания.
2. Браузер отправляет JSON в `POST /api/chat`.
3. Web-слой находит отдельного агента по cookie или создаёт нового.
4. Web-слой передаёт агенту текст, модель и необязательные параметры.
5. Агент применяет Sliding Window, обновляет Sticky Facts либо выбирает состояние
   активной ветки Branching.
6. Агент считает токены запроса и активной истории, сравнивает их с лимитом
   модели и при переполнении создаёт предупреждение без блокировки запроса.
7. Агент передаёт явное окно/facts либо продолжает отдельную API-цепочку ветки;
   затем вызывает `agent.LLM` независимо от результата сравнения с лимитом.
8. OpenAI-клиент преобразует запрос в HTTP-вызов Responses API и возвращает
   транспортно-независимый результат.
9. Агент рассчитывает длительность, фактические и накопленные токены и стоимость, добавляет пару сообщений и
   сохраняет сообщения, модель и новый ID в JSON.
10. Браузер отображает ответ и метрики хода под сообщением, а метрики диалога и
   предупреждение — в левой панели; после перезапуска `/api/history`
   восстанавливает тот же транскрипт, а новый запрос продолжает прежнюю цепочку.

## Безопасность

- сервер по умолчанию слушает только `127.0.0.1`;
- Docker публикует порт только на loopback-интерфейсе;
- API-ключ остаётся в окружении Go-процесса;
- POST-маршруты требуют служебный заголовок и проверяют `Origin`;
- включены CSP, запрет iframe, `nosniff` и строгая cookie;
- размер JSON-запроса ограничен 1 МиБ;
- файл истории создаётся с правами `0600` и не попадает в Git;
- Markdown-рендерер создаёт только разрешённые DOM-элементы, а содержимое вставляет как текст; сырой HTML не исполняется, ссылки фильтруются по протоколу.

`store: true` необходим текущей схеме с `previous_response_id`. Это означает,
что ответы могут храниться на стороне OpenAI согласно политике Responses API,
даже если локальный сервер не пишет транскрипт на диск.

## Ограничения

- ответы приходят целиком, без token streaming;
- JSON-хранилище рассчитано на один процесс приложения и не использует
  межпроцессные блокировки;
- история хранится локально без шифрования диска;
- Markdown-рендерер намеренно не поддерживает сырой HTML и загрузку внешних изображений;
- нет аутентификации пользователей: приложение рассчитано на локальный запуск;
- автоматические повторы для временных ошибок API пока не реализованы.
