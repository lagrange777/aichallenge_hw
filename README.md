# Codex Chat Web

Локальный веб-интерфейс на Go для диалога с Codex-моделью через OpenAI
Responses API. API-ключ остаётся на сервере и никогда не передаётся в браузер.
Логика обращения к LLM и обработки ответа инкапсулирована в отдельной сущности
`agent.Agent`; web-слой не зависит от деталей OpenAI API.

## Возможности

- RAG в чате, источники под ответом и сравнение двух режимов на 10 вопросах
  во вкладке «RAG» ([описание и запуск](RAG.md));

- локальная индексация документов: OpenAI Embeddings, SQLite, две стратегии
  chunking, сравнение поиска и вкладка «Документы» ([инструкция](documents/README.md));

- адаптивный интерфейс для компьютера и телефона;
- отдельный агент для каждого браузерного диалога;
- многострочный ввод: `Enter` отправляет, `Shift+Enter` добавляет строку;
- отдельный контекст для каждого браузера через защищённую cookie;
- история сообщений в локальном JSON-файле;
- автоматическое восстановление контекста и переписки после перезапуска приложения;
- безопасное отображение Markdown: заголовки, списки, таблицы, цитаты, ссылки и блоки кода;
- выбор модели перед отправкой сообщения;
- перенос всей сохранённой истории в контекст новой модели при переключении;
- время ответа, расход токенов и ориентировочная стоимость под каждым ответом;
- точный предварительный подсчёт токенов текущего запроса и активной истории;
- заполнение контекстного окна и накопленные токены/стоимость всего диалога в левой панели;
- неблокирующее предупреждение при превышении входного лимита модели;
- режим «Без стратегии» с полной историей и три стратегии контекста: Sliding Window, Sticky Facts и Branching;
- отдельная память важных фактов и независимые ветки от общего checkpoint;
- профили пользователя с настройками языка, стиля, подробности, формата и ограничений;
- отдельные задачи и память для каждого профиля, снимок настроек под каждым ответом;
- три отдельных слоя памяти: переписка, данные задачи и долговременный профиль;
- просмотр памяти по вкладкам: диалог, рабочая, долговременная, предложения и история решений;
- поиск по записям, карточки с источником и редактирование по нажатию;
- предложения памяти с подтверждением, выбором слоя, редактированием и отклонением;
- кнопки под каждым сообщением для прямого сохранения в рабочую или долговременную память;
- сохранённые задачи с переключением между их диалогами, рабочей памятью и стратегиями контекста;
- новый диалог без перезапуска сервера;
- встроенные CSS и JavaScript без внешних frontend-зависимостей.

## Требования

- Go 1.25 или новее;
- OpenAI API key с доступом к выбранной модели;
- настроенный биллинг OpenAI API, если он требуется для аккаунта.

Подписка ChatGPT и биллинг OpenAI API — отдельные продукты.

## Локальный запуск

```sh
export OPENAI_API_KEY="your-api-key"
go run ./cmd/codex-chat
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080). Для остановки
сервера нажмите `Ctrl+C`.

Приложение читает ключ только из `OPENAI_API_KEY`. Не добавляйте настоящий ключ
в исходники или командную историю.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `OPENAI_MODEL` | `gpt-5.3-codex` | модель по умолчанию; также добавляется в список выбора, если это пользовательский ID |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | базовый URL API |
| `OPENAI_TIMEOUT` | `2m` | тайм-аут одного запроса |
| `WEB_ADDR` | `127.0.0.1:8080` | адрес локального HTTP-сервера |
| `RAG_REPORT_PATH` | `artifacts/rag/comparison.json` | сохранённое сравнение ответов во вкладке RAG |
| `HISTORY_PATH` | `data/history.json` | путь к JSON-файлу с историями диалогов |
| `PROFILE_PATH` | `profiles` рядом с файлом истории | реестр профилей и активный профиль браузера |
| `MCP_PATH` | `mcp.json` рядом с файлом истории | подключения MCP, общие для локального экземпляра приложения |
| `BROKER_DEMO_ORDER_MCP` | пусто | endpoint demo-сервиса заявок; при указании подключение и его инструменты автоматически регистрируются для чата |
| `BROKER_DEMO_VALIDATION_MCP` | пусто | endpoint demo-сервиса проверки заявок |
| `BROKER_DEMO_BROKER_MCP` | пусто | endpoint demo-брокера |
| `BROKER_DEMO_SECRET` | `local-demo-secret-change-me` | общий секрет подписи данных между тремя demo-серверами |
| `MEMORY_PATH` | `memory` рядом с файлом истории | каталог рабочей и долговременной памяти, текущей задачи и предложений |
| `CONTEXT_STRATEGY` | `sliding_window` | режим по умолчанию: `none`, `sliding_window`, `sticky_facts` или `branching` |
| `CONTEXT_KEEP_LAST` | `10` | число последних сообщений для Sliding Window и Sticky Facts |

Перед первым сообщением эти настройки можно изменить прямо на стартовом экране:
выбрать режим «Без стратегии» или одну из трёх стратегий. Поле «Последние N
сообщений» показывается только для Sliding Window и Sticky Facts. После начала
диалога настройки фиксируются, сохраняются вместе с
историей и восстанавливаются после перезапуска. Кнопка «Новый диалог» снова
открывает их для редактирования.

## Запуск в Docker

Самый удобный вариант — создать локальный `.env` из примера и заполнить ключ:

```sh
cp .env.example .env
docker compose up --build
```

После запуска откройте [http://127.0.0.1:8080](http://127.0.0.1:8080).
Compose публикует порт только на loopback-интерфейсе компьютера. Файл `.env`
исключён из Git и из контекста Docker-сборки. История хранится в именованном
томе `chat-history`, поэтому не исчезает при пересоздании контейнера.

Сборка без Compose:

```sh
docker build -t codex-chat-web:local .
docker volume create codex-chat-history
docker run --rm \
  -p 127.0.0.1:8080:8080 \
  -e OPENAI_API_KEY \
  -e WEB_ADDR=0.0.0.0:8080 \
  -e HISTORY_PATH=/data/history.json \
  -v codex-chat-history:/data \
  codex-chat-web:local
```

## HTTP-маршруты

- `GET /` — веб-интерфейс;
- `POST /api/chat` — отправка сообщения;
- `GET /api/history` — восстановление сообщений текущего браузерного диалога;
- `POST /api/reset` — сброс контекста текущего браузера;
- `GET /api/memory` — память активной задачи, общий профиль и список задач;
- `POST /api/tasks/new` — создать задачу (`taskId` текущей задачи, `name` новой);
- `GET /api/profiles` — профили, примеры настроек и состояние активного профиля;
- `POST /api/profiles/new` — создать профиль;
- `POST /api/profiles/edit` — обновить профиль;
- `POST /api/profiles/switch` — переключить профиль и восстановить его данные;
- `POST /api/tasks/switch` — открыть сохранённую задачу (`taskId` текущей задачи, `id` выбранной);
- `POST /api/branches/create` — checkpoint и две независимые ветки;
- `POST /api/branches/switch` — переключение активной ветки;
- `GET /api/status` — модель по умолчанию и доступный список моделей;
- `GET /healthz` — проверка готовности сервера.

`POST /api/chat` принимает обязательное поле `message`, выбранную модель `model`, три необязательных
строковых поля (`responseFormat`, `lengthLimit`, `completionCondition`) и
необязательное числовое поле `temperature` от 0 до 2. Непустые строковые
значения добавляются к обязательным требованиям текущего ответа, а температура
передаётся отдельным параметром Responses API. Если `message` пустое, запрос к
модели не выполняется независимо от дополнительных полей.

В первом запросе диалога также можно передать `contextStrategy` и
`contextKeepLast` (целое число от 1 до 1000). Допустимые стратегии:
`none`, `sliding_window`, `sticky_facts`, `branching`. Для `none` и `branching`
параметр `contextKeepLast` не используется и интерфейс его не отправляет. Следующие запросы могут повторять
те же значения, но попытка изменить их после первого успешного сообщения
вернёт HTTP 409.

Успешный ответ `/api/chat` содержит текст, фактическую модель и метрики:
время обработки на сервере, входные/выходные/кэшированные токены, токены
рассуждения, общее число токенов и расчётную стоимость. Стоимость вычисляется
по публичным тарифам OpenAI, актуальным на 2026-09-06, и не включает отдельную
плату за инструменты. Для пользовательской модели с неизвестным тарифом
интерфейс показывает, что стоимость неизвестна. Метрики отдельного хода
отображаются под ответом, а размер истории, заполнение контекста и накопленные
значения всего диалога — в левой панели.

Перед генерацией приложение вызывает `POST /v1/responses/input_tokens`. Отдельно
считаются текущий запрос и полный запрос с активным контекстом: через
`previous_response_id` либо через массив сохранённых сообщений при смене модели.
Разница показывает размер активной истории, а полный результат — заполнение
контекстного окна. Эти предварительные значения дополняются фактическими
`usage.input_tokens` и `usage.output_tokens` после ответа.

Sliding Window и Sticky Facts всегда формируют явный массив сообщений и не
передают `previous_response_id`. Это гарантирует, что отброшенная история не
вернётся через серверную цепочку Responses API. Branching хранит отдельный
транскрипт каждой ветки. При подключённых слоях памяти (по умолчанию в приложении)
он тоже передаётся явно вместе с актуальными подтверждёнными записями.

## Стратегии управления контекстом

Независимо от стратегии агент использует подтверждённую рабочую и долговременную
память. После ответа кнопка «Память» показывает предложения: только вы решаете,
что и в какой слой сохранить. «Новый чат» очищает переписку, а «Новая задача»
на отдельной вкладке «Задачи» также очищает рабочий слой; профиль сохраняется.
Модель, хранение, API и сценарий проверки описаны в [MEMORY.md](MEMORY.md).

### Без стратегии

В модель передаются вся сохранённая история диалога и новый запрос явным
массивом сообщений, без `previous_response_id`, сокращения, facts или веток.
Подтверждённые слои памяти добавляются отдельно.
Режим сохраняется после перезапуска; при смене модели полная история также
передаётся новой модели. Параметр N не применяется. По умолчанию по-прежнему
выбран Sliding Window.

### Sliding Window

В модель передаются только последние N сообщений и новый запрос. Более старые
сообщения остаются в локальном JSON для отображения, но полностью исключаются
из контекста модели. Дополнительных вызовов API нет.

### Sticky Facts / Key-Value Memory

Перед каждым основным ответом агент отдельным вызовом обновляет JSON-объект
`facts`. В нём сохраняются цель, ограничения, предпочтения, решения и
договорённости. Основной запрос получает developer-блок с актуальными facts и
последние N сообщений. Facts сохраняются отдельно в `history.json` и видны в
левой панели. Токены вызовов обновления памяти включены в общие метрики.

### Branching

После общей части диалога кнопка «Создать checkpoint и 2 ветки» клонирует
текущий транскрипт и `response_id` в «Ветку A» и «Ветку B». Дальнейшие ответы,
история веток независима; подтверждённые слои памяти общие для текущей задачи. Переключатель в левой панели мгновенно
восстанавливает выбранную ветку; обе ветки сохраняются между перезапусками.

### Сценарий сравнения на 12 сообщениях

Используйте одинаковое N, например 4, и трижды пройдите один сценарий сбора ТЗ:

1. Зафиксируйте цель продукта, аудиторию, платформу и срок.
2. Добавьте ограничения по бюджету, безопасности и интеграциям.
3. Обсудите два варианта архитектуры и выберите один.
4. Добавьте несколько второстепенных уточнений, чтобы ранние факты вышли из окна.
5. Попросите составить итоговое ТЗ со всеми исходными ограничениями.
6. Для Branching создайте checkpoint перед выбором архитектуры, рассмотрите
   разные варианты в A и B, затем сравните финальные ТЗ.

| Стратегия | Качество и стабильность | Токены | Удобство |
|---|---|---|---|
| Sliding Window | хорошо помнит недавнее, ранние детали теряются после выхода из N | минимальный расход | самая простая |
| Sticky Facts | стабильно сохраняет важные ранние факты, но зависит от качества извлечения | окно меньше, но есть дополнительный вызов facts | facts видны и проверяемы |
| Branching | каждая версия решения последовательна и не загрязняет соседнюю | расход считается отдельно в каждой ветке | удобно сравнивать альтернативы |

Автоматические тесты проверяют ограничение окна, обновление facts после каждого
сообщения, независимость веток и восстановление всех стратегий после
перезапуска. Для чистого ручного сравнения начинайте новый диалог перед каждой
стратегией.

Если расчётный вход превышает лимит выбранной модели, интерфейс показывает
жёлтое предупреждение, но агент всё равно отправляет запрос. При стандартной
стратегии Responses API модель может отклонить такой запрос с HTTP 400; ошибка
будет показана рядом с предупреждением. Неуспешный ход в историю не записывается.

## Проверка роста токенов

- **Короткий диалог:** отправьте 2–3 коротких вопроса и сравните поля «запрос»,
  «история», «ответ» и «диалог».
- **Длинный диалог:** продолжайте один диалог; «история», доля контекста,
  накопленные токены и стоимость будут расти.
- **Переполнение:** автоматический тест использует вход 300 000 токенов при
  лимите 272 000 и проверяет, что предупреждение появляется, но LLM всё равно
  вызывается:

```sh
go test ./internal/agent -run TestAgentComparesShortLongAndOverflowDialogs -v
go test ./internal/agent -run 'TestSlidingWindow|TestStickyFacts|TestBranching' -v
```

## Проверка

### MCP-подключения

Откройте вкладку **MCP**. Кнопка «Добавить Neurly» заполняет адрес
`https://neurly.ru/v1/mcp`; введите API-ключ Neurly и сохраните подключение.
В [кабинете Neurly](https://neurly.ru/dashboard/integrations) предварительно
включите нужную интеграцию. Например, «Московская биржа» предоставляет инструменты
публичных данных без отдельного ключа биржи. По [документации Neurly](https://neurly.ru/docs/mcp)
для доступа к MCP нужен положительный баланс аккаунта, сами MCP-вызовы бесплатны.

Нажмите **«Проверить и получить инструменты»** во вкладке подключения.
Приложение через официальный `github.com/modelcontextprotocol/go-sdk` v1.7.0
согласует протокол MCP, получает все страницы `tools/list` и показывает имя,
версию сервера, число инструментов, их описания и JSON-схемы параметров.
У каждого сервера своя вкладка с настройками и результатом проверки. Черновики настроек и результаты сохраняются при переключении вкладок до перезагрузки страницы. В интерфейсе есть поиск по инструментам. Пустой список отображается отдельно;
он означает успешное соединение без доступных инструментов.

Поддерживаются удалённые серверы **Streamable HTTP**, Bearer-ключ или отсутствие
авторизации. «Другой MCP-сервер» позволяет указать произвольный HTTPS endpoint;
HTTP разрешён для локального сервера (`localhost`, `127.0.0.1`, `::1`) и точных адресов из переменной `MCP_HTTP_ENDPOINTS` (через запятую).
OAuth и запуск stdio-серверов не поддерживаются. Для использования в чате отметьте
нужные инструменты, включите **«Использовать в чате»** и нажмите **«Сохранить разрешения»**.
Поддерживаются инструменты с аннотацией `readOnlyHint: true`. Изменения разрешены
только для явно перечисленных инструментов локальных demo-серверов: сохранение
отчёта в `mock-issue-mcp` и операции учебного брокерского flow. Остальные
инструменты записи недоступны. Перед каждым изменением приложение повторно
проверяет имя сервера, имя инструмента, аннотации и актуальное разрешение.
Аннотация — декларация сервера, поэтому подключайте доверенные серверы.
По умолчанию новые и ранее сохранённые подключения выключены для чата.
При изменении адреса или ключа разрешения сбрасываются.
Проверка ограничена 30 секундами и закрывает MCP-сессию после получения списка;
показанный результат — снимок последней проверки, а не постоянное соединение.

Настройки общие для всех браузеров и профилей **одного локального экземпляра**.
Файл `MCP_PATH` хранит ключи открытым текстом с правами `0600` и атомарно заменяется
при сохранении. По умолчанию он находится в исключённом из Git каталоге `data`.
Ключи не возвращаются в API, не сохраняются в localStorage и не передаются LLM.
Пустое поле ключа при редактировании сохраняет прежний ключ; отдельная галочка
удаляет его. При смене URL старый ключ сбрасывается — введите подходящий заново.
HTTP-перенаправления не выполняются. В Docker настройки хранятся в томе `/data`.

Маршруты: `GET /api/mcp`, `POST /api/mcp/save`, `POST /api/mcp/delete`,
`POST /api/mcp/check`, `POST /api/mcp/permissions`. Все требуют `X-Codex-Chat: 1` и проходят проверку Origin.
Изменение, удаление и проверка используют версию подключения для защиты от устаревших форм.

Автоматические тесты проверяют MCP-соединение с локальным SDK-сервером (JSON и SSE),
совместимость с `initialize`, пагинацию, Bearer-авторизацию, ошибки, сохранение
после перезапуска и отсутствие ключа в ответах API:

```sh
go test ./internal/mcpclient ./internal/web
```

### Mock MCP и вызов из чата

Mock Issue Tracker — отдельный проект `../mock-issue-mcp`, отдельный образ,
контейнер и REST API. Сначала запустите его, чтобы создать сеть `codex-mcp`:

```sh
docker compose -f ../mock-issue-mcp/compose.yaml up -d --build
docker compose up -d --build
```

Если mock не нужен, сеть можно создать отдельно: `docker network create codex-mcp`.
Приложение подключается к внешней сети; остановка mock не удаляет данные чата.

В веб-интерфейсе MCP → «Добавить сервер» → **Mock Issue Tracker**:

1. Сохраните адрес `http://mock-issue-mcp:8090/mcp`, ключ оставьте пустым.
2. Нажмите «Проверить и получить инструменты».
3. Отметьте `search_issues`, `get_issue`, `get_issue_comments`.
4. Включите «Использовать в чате», сохраните разрешения.
5. В чате спросите: **«Почему заблокирована задача DEMO-101 и кто может помочь?»**

Для демонстрации композиции также отметьте `summarize_issues` и
`save_issue_report`, затем отправьте:

> Найди заблокированные задачи проекта DEMO, собери Markdown-отчёт и сохрани его
> как blocked-demo.md.

Ожидаемая автоматическая цепочка:
`search_issues` → `summarize_issues` → `save_issue_report`. Результат каждого
шага возвращается модели через `function_call_output` и становится аргументом
следующего инструмента. Последний вызов разрешён только после явного выбора
`save_issue_report` в настройках MCP.

Для приложения вне Docker используйте `http://localhost:8090/mcp`.
Ожидаемая цепочка: `get_issue(DEMO-101)` → `get_issue(DEMO-100)` →
`get_issue_comments(DEMO-100)`. Модель выбирает порядок и число вызовов сама.
Результат: блокировка связана с отсутствием sandbox-ключа платежного провайдера;
помочь может ответственный за DEMO-100 Алексей, запрос ключа уже отправлен.

Агент получает актуальный `tools/list`, передаёт выбранные схемы в Responses API,
обрабатывает `function_call`, вызывает MCP `tools/call`, возвращает
`function_call_output` по `call_id` и продолжает до текстового ответа.
`previous_response_id` сохраняет контекст промежуточных вызовов.
Аргументы проверяются по JSON Schema; разрешения и версия подключения повторно
проверяются перед каждым вызовом. Системные запросы памяти и проверок не получают
инструменты. Инварианты проверяются до выполнения вызова и после итогового ответа.

Лимиты: 64 инструмента в запросе, 6 попыток вызова на сообщение, 30 секунд на MCP
операцию, 3 минуты на цикл модели с инструментами, 16 КиБ аргументов и 32 КиБ
результата. Ошибки возвращаются модели и отображаются в журнале. Журнал **MCP**
под ответом содержит сервер, инструмент, аргументы, результат, время и ошибку;
он сохраняется в истории. Токены всех промежуточных обращений учитываются в метриках.
Результаты MCP передаются модели и сохраняются в истории как пользовательские данные.

Проверка интеграции без платных API-вызовов:

```sh
go test ./...
```

Тесты проверяют MCP SDK-соединение, схему аргументов, отзыв доступа,
формат function calling, автоматическую цепочку search → summarize → save,
точную передачу результата между шагами, лимит вызовов и журнал.

### Длинный flow через три MCP-сервера

В проект входит локальная брокерская демонстрация с тремя независимыми
MCP-серверами и отдельными SQLite-базами:

| MCP-сервер | Инструменты | Ответственность |
|---|---|---|
| `demo-order-mcp` | `create_buy_order`, `get_order`, `list_my_orders`, `record_order_execution`, `record_validation_rejection` | заявки и их статусы |
| `demo-validation-mcp` | `validate_order` | наличие инструмента, доступный объём и цена |
| `demo-broker-mcp` | `execute_validated_order`, `get_account`, `get_portfolio` | списание денег, сделки и портфель |

Фонового обработчика здесь нет. Агент сам выбирает инструменты и за один запрос
выполняет цепочку в порядке зависимостей:

```text
create_buy_order
  → validate_order
    → execute_validated_order
      → record_order_execution
        → get_account
          → get_portfolio
```

Между сервисами передаются подписанные HMAC-токены:
`orderToken → validationToken → executionToken`. Получатель проверяет подпись и
извлекает из токена ID заявки, тикер, количество и цену, поэтому агент не может
незаметно изменить их между шагами. Создание заявки использует `requestId`, а
покупка — уникальный `orderId`, поэтому повторный вызов не создаёт вторую заявку
или сделку. Ветка с `REJECTED` записывает отказ в сервис заявок и не вызывает
брокер.

В демонстрации есть только пользователь `demo-user` со стартовым балансом
1 000 000 RUB. Данные биржи фиксированы для воспроизводимой проверки: например,
SBER стоит 318,50 RUB. Это локальная симуляция без подключения к реальной бирже.

Запуск через Compose автоматически регистрирует все три подключения и выдаёт
агенту точные разрешения на их инструменты:

```sh
docker network create codex-mcp 2>/dev/null || true
docker compose up --build
```

После запуска отправьте в чат:

> Купи 10 SBER не дороже 320 рублей за штуку. После исполнения покажи статус
> заявки, остаток счёта и портфель.

Ожидаются шесть MCP-вызовов из схемы выше. Итоговый статус — `FILLED`, остаток —
996 811,81 RUB с учётом комиссии 0,1%, в портфеле — 10 SBER по средней цене
318,50 RUB. Запрос «Покажи мои заявки, счёт и портфель» использует инструменты
чтения соответствующих серверов.

Автоматическая проверка поднимает три настоящих MCP HTTP handler, проходит
успешную и отклонённую ветки, проверяет токены, порядок маршрутизации,
идемпотентность, баланс и портфель:

```sh
go test ./internal/brokerdemo ./internal/agent ./internal/mcpclient
```

### Универсальные фоновые задачи MCP

Вкладка **«Фоновые задачи»** запускает инструмент чтения любого сохранённого
MCP-сервера по расписанию. Поля параметров строятся по `inputSchema`; вложенные,
составные и свободные схемы доступны как JSON-объект. Сервер проверяет схему
перед сохранением и каждым вызовом. В список попадают только инструменты с
`readOnlyHint: true`. Инструменты изменения внешних данных пока не поддерживаются.

1. Выберите MCP-сервер и инструмент, заполните параметры.
2. Задайте расписание: один раз, каждые N минут или ежедневно в указанном часовом
   поясе IANA (например, `Asia/Novosibirsk`). Разовая дата в форме — в поясе браузера.
3. Выберите обработку: сохранить ответ, дополнительно сделать сводку после каждого
   запуска или собирать сводку за период. Можно задать собственную инструкцию.
4. Нажмите **«Пробный запуск»**, чтобы вызвать инструмент без создания задачи.
5. Создайте задачу. Для интервала первый запуск сразу; для ежедневного расписания
   выбирается ближайшее будущее время. Результаты видны в **«Результаты и журнал»**.

Доступны пауза, возобновление, редактирование, удаление с историей и запуск сейчас.
Последний ставит активную задачу в очередь и сохраняет будущее расписание.
Разовая задача после успеха или трёх ошибок становится завершённой; для повторения
нужно отредактировать её расписание. Редактирование начинает новый период сводки,
сохраняет историю и состояние паузы, обновляет привязку к версии MCP-подключения.

Шаблон **«Обзор рынка — Мосбиржа»** заполняет параметры `moex_quotes` для TQBR,
SBER/GAZP/LKOH и интервалы 30/60 минут. Для него выберите сервер с этим инструментом
(например, Neurly с включённой интеграцией Мосбиржи). Это опциональный обработчик
`processor: "market"`: он вычисляет первую/последнюю цену, min/max и изменение по
наблюдениям; модель получает готовые агрегаты. Повторные снимки внутри сводки
дедуплицируются по тикеру и времени источника. Отсутствующие цены не заменяются
нулями; задержанные данные и неактивные торги отмечаются. Это не биржевые OHLC.
Старые наблюдения и их расчётная история продолжают работать; редактирование
переводит старое наблюдение в универсальную модель задачи.

**Управление через агента.** Включите «Разрешить агенту управлять заданиями через
MCP». Это отдельное разрешение проекта. Его отключение запрещает изменения из
чата, но не останавливает существующие задачи. Настройка источника «Использовать
в чате» для фона не требуется: задача отдельно разрешает конкретный вызов.
Ключи остаются в настройках MCP, в задаче сохраняется ID и версия подключения.

Например:

> Через mock MCP каждый час получай открытые задачи и делай сводку результатов
> каждые три часа. Назови задание «Открытые задачи».

Агент использует настоящий MCP SDK и инструменты:

- `list_scheduled_tasks` — задачи, статусы и подключённые серверы;
- `list_schedulable_tools` — инструменты чтения сервера и их схемы;
- `create_scheduled_task` — создание;
- `get_task_results` — последняя сводка и последние пять запусков с ответами;
- `pause_scheduled_task` — пауза/возобновление;
- `update_scheduled_task` — редактирование полного `spec`;
- `run_scheduled_task` — запуск сейчас;
- `delete_scheduled_task` — удаление задачи с историей.

Пример аргументов `create_scheduled_task` (имя инструмента и параметры берутся
из реального `list_schedulable_tools` выбранного сервера):

```json
{
  "name": "Открытые задачи",
  "connectionId": "ID сохранённого MCP-сервера",
  "toolName": "list_issues",
  "arguments": {"status": "open"},
  "schedule": {"kind": "interval", "intervalSeconds": 3600},
  "summaryMode": "period",
  "summarySeconds": 10800,
  "summaryPrompt": "Выдели изменения и задачи, требующие внимания",
  "requestId": "open-issues-v1"
}
```

Другие расписания: `{"kind":"once","at":1791000000}` (будущее Unix-время) и
`{"kind":"daily","time":"18:00","timezone":"Europe/Moscow"}`.
`summaryMode`: `none`, `each`, `period`. Для разовой задачи доступны `none`/`each`.
Повторный `requestId` с теми же параметрами возвращает прежнюю задачу. Если он
не задан, ключ вычисляется из параметров. Для изменений требуются ID и версия.

MCP также доступен через Streamable HTTP на `/mcp/scheduler` с заголовком
`X-Codex-Chat: 1` и проверкой Origin. HTTP `tools/list` возвращает все восемь
инструментов, но обработчики изменений проверяют разрешение. В каталоге агента
они появляются только при включённом разрешении.

**Выполнение и хранение:**

- SQLite: `SCHEDULER_PATH`, по умолчанию `data/scheduler.db`, в Docker
  `/data/scheduler.db` в постоянном томе. WAL, атомарное сохранение результатов.
- Обработчик работает внутри web-сервера независимо от браузера. Docker использует
  `restart: unless-stopped`; для 24/7 хост должен работать и не спать.
- Lease на пять минут исключает одновременную обработку одной задачи. После аварии
  чтение может повториться: гарантия exactly-once для внешнего вызова не заявляется.
- Пропущенные интервалы объединяются в один актуальный запуск. Пауза, изменение
  или удаление аннулируют результаты уже начатой обработки.
- При ошибке — повторы через 30 и 60 секунд, затем следующее время по расписанию.
  При переходе летнего времени отсутствующее локальное время пропускается,
  повторяющееся время выполняется один раз за календарный день.
- После изменения настроек MCP старая версия перестаёт вызываться; сохраните
  задачу заново через «Изменить», чтобы принять актуальное подключение.
- До 20 задач. Интервалы запуска и сводки: 60–86400 секунд. Параметры до 12 КиБ,
  исходный ответ до 32 КиБ: слишком большой ответ становится явной ошибкой,
  нужно сузить выборку инструмента. Сохраняются 1500 запусков и 100 сводок на задачу;
  интерфейс показывает последние 100 записей. История содержит исходные ответы.
- Модель получает до 64 КиБ последних результатов периода, при неполной выборке
  сохраняется предупреждение. Ответы инструментов трактуются как недоверенные
  данные, модель не получает инструменты. Ошибка модели не теряет исходные ответы:
  сохраняется сводка количества успешных/неуспешных запусков.
- Сводки используют `OPENAI_MODEL`; модель и расход токенов сохраняются рядом
  со сводкой. При отключённых сводках обращений к модели нет.
