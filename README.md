# Codex Chat Web

Локальный веб-интерфейс на Go для диалога с Codex-моделью через OpenAI
Responses API. API-ключ остаётся на сервере и никогда не передаётся в браузер.
Логика обращения к LLM и обработки ответа инкапсулирована в отдельной сущности
`agent.Agent`; web-слой не зависит от деталей OpenAI API.

## Возможности

- адаптивный интерфейс для компьютера и телефона;
- отдельный агент для каждого браузерного диалога;
- многострочный ввод: `Enter` отправляет, `Shift+Enter` добавляет строку;
- отдельный контекст для каждого браузера через защищённую cookie;
- история сообщений в локальном JSON-файле;
- автоматическое восстановление контекста и переписки после перезапуска приложения;
- безопасное отображение Markdown: заголовки, списки, таблицы, цитаты, ссылки и блоки кода;
- выбор модели перед отправкой сообщения;
- перенос всей сохранённой истории в контекст новой модели при переключении;
- время ответа, расход токенов и ориентировочная стоимость под каждым ответом;
- точный предварительный подсчёт токенов текущего запроса и активной истории;
- заполнение контекстного окна и накопленные токены/стоимость всего диалога в левой панели;
- неблокирующее предупреждение при превышении входного лимита модели;
- режим «Без стратегии» с полной историей и три стратегии контекста: Sliding Window, Sticky Facts и Branching;
- отдельная память важных фактов и независимые ветки от общего checkpoint;
- три отдельных слоя памяти: переписка, данные задачи и долговременный профиль;
- просмотр памяти по вкладкам: диалог, рабочая, долговременная, предложения и история решений;
- поиск по записям, карточки с источником и редактирование по нажатию;
- предложения памяти с подтверждением, выбором слоя, редактированием и отклонением;
- кнопки под каждым сообщением для прямого сохранения в рабочую или долговременную память;
- сохранённые задачи с переключением между их диалогами, рабочей памятью и стратегиями контекста;
- новый диалог без перезапуска сервера;
- встроенные CSS и JavaScript без внешних frontend-зависимостей.

## Требования

- Go 1.22 или новее;
- OpenAI API key с доступом к выбранной модели;
- настроенный биллинг OpenAI API, если он требуется для аккаунта.

Подписка ChatGPT и биллинг OpenAI API — отдельные продукты.

## Локальный запуск

```sh
export OPENAI_API_KEY="your-api-key"
go run ./cmd/codex-chat
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080). Для остановки
сервера нажмите `Ctrl+C`.

Приложение читает ключ только из `OPENAI_API_KEY`. Не добавляйте настоящий ключ
в исходники или командную историю.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `OPENAI_MODEL` | `gpt-5.3-codex` | модель по умолчанию; также добавляется в список выбора, если это пользовательский ID |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | базовый URL API |
| `OPENAI_TIMEOUT` | `2m` | тайм-аут одного запроса |
| `WEB_ADDR` | `127.0.0.1:8080` | адрес локального HTTP-сервера |
| `HISTORY_PATH` | `data/history.json` | путь к JSON-файлу с историями диалогов |
| `MEMORY_PATH` | `memory` рядом с файлом истории | каталог рабочей и долговременной памяти, текущей задачи и предложений |
| `CONTEXT_STRATEGY` | `sliding_window` | режим по умолчанию: `none`, `sliding_window`, `sticky_facts` или `branching` |
| `CONTEXT_KEEP_LAST` | `10` | число последних сообщений для Sliding Window и Sticky Facts |

Перед первым сообщением эти настройки можно изменить прямо на стартовом экране:
выбрать режим «Без стратегии» или одну из трёх стратегий. Поле «Последние N
сообщений» показывается только для Sliding Window и Sticky Facts. После начала
диалога настройки фиксируются, сохраняются вместе с
историей и восстанавливаются после перезапуска. Кнопка «Новый диалог» снова
открывает их для редактирования.

## Запуск в Docker

Самый удобный вариант — создать локальный `.env` из примера и заполнить ключ:

```sh
cp .env.example .env
docker compose up --build
```

После запуска откройте [http://127.0.0.1:8080](http://127.0.0.1:8080).
Compose публикует порт только на loopback-интерфейсе компьютера. Файл `.env`
исключён из Git и из контекста Docker-сборки. История хранится в именованном
томе `chat-history`, поэтому не исчезает при пересоздании контейнера.

Сборка без Compose:

```sh
docker build -t codex-chat-web:local .
docker volume create codex-chat-history
docker run --rm \
  -p 127.0.0.1:8080:8080 \
  -e OPENAI_API_KEY \
  -e WEB_ADDR=0.0.0.0:8080 \
  -e HISTORY_PATH=/data/history.json \
  -v codex-chat-history:/data \
  codex-chat-web:local
```

## HTTP-маршруты

- `GET /` — веб-интерфейс;
- `POST /api/chat` — отправка сообщения;
- `GET /api/history` — восстановление сообщений текущего браузерного диалога;
- `POST /api/reset` — сброс контекста текущего браузера;
- `GET /api/memory` — память активной задачи, общий профиль и список задач;
- `POST /api/tasks/new` — создать задачу (`taskId` текущей задачи, `name` новой);
- `POST /api/tasks/switch` — открыть сохранённую задачу (`taskId` текущей задачи, `id` выбранной);
- `POST /api/branches/create` — checkpoint и две независимые ветки;
- `POST /api/branches/switch` — переключение активной ветки;
- `GET /api/status` — модель по умолчанию и доступный список моделей;
- `GET /healthz` — проверка готовности сервера.

`POST /api/chat` принимает обязательное поле `message`, выбранную модель `model`, три необязательных
строковых поля (`responseFormat`, `lengthLimit`, `completionCondition`) и
необязательное числовое поле `temperature` от 0 до 2. Непустые строковые
значения добавляются к обязательным требованиям текущего ответа, а температура
передаётся отдельным параметром Responses API. Если `message` пустое, запрос к
модели не выполняется независимо от дополнительных полей.

В первом запросе диалога также можно передать `contextStrategy` и
`contextKeepLast` (целое число от 1 до 1000). Допустимые стратегии:
`none`, `sliding_window`, `sticky_facts`, `branching`. Для `none` и `branching`
параметр `contextKeepLast` не используется и интерфейс его не отправляет. Следующие запросы могут повторять
те же значения, но попытка изменить их после первого успешного сообщения
вернёт HTTP 409.

Успешный ответ `/api/chat` содержит текст, фактическую модель и метрики:
время обработки на сервере, входные/выходные/кэшированные токены, токены
рассуждения, общее число токенов и расчётную стоимость. Стоимость вычисляется
по публичным тарифам OpenAI, актуальным на 2026-09-06, и не включает отдельную
плату за инструменты. Для пользовательской модели с неизвестным тарифом
интерфейс показывает, что стоимость неизвестна. Метрики отдельного хода
отображаются под ответом, а размер истории, заполнение контекста и накопленные
значения всего диалога — в левой панели.

Перед генерацией приложение вызывает `POST /v1/responses/input_tokens`. Отдельно
считаются текущий запрос и полный запрос с активным контекстом: через
`previous_response_id` либо через массив сохранённых сообщений при смене модели.
Разница показывает размер активной истории, а полный результат — заполнение
контекстного окна. Эти предварительные значения дополняются фактическими
`usage.input_tokens` и `usage.output_tokens` после ответа.

Sliding Window и Sticky Facts всегда формируют явный массив сообщений и не
передают `previous_response_id`. Это гарантирует, что отброшенная история не
вернётся через серверную цепочку Responses API. Branching хранит отдельный
транскрипт каждой ветки. При подключённых слоях памяти (по умолчанию в приложении)
он тоже передаётся явно вместе с актуальными подтверждёнными записями.

## Стратегии управления контекстом

Независимо от стратегии агент использует подтверждённую рабочую и долговременную
память. После ответа кнопка «Память» показывает предложения: только вы решаете,
что и в какой слой сохранить. «Новый чат» очищает переписку, а «Новая задача»
на отдельной вкладке «Задачи» также очищает рабочий слой; профиль сохраняется.
Модель, хранение, API и сценарий проверки описаны в [MEMORY.md](MEMORY.md).

### Без стратегии

В модель передаются вся сохранённая история диалога и новый запрос явным
массивом сообщений, без `previous_response_id`, сокращения, facts или веток.
Подтверждённые слои памяти добавляются отдельно.
Режим сохраняется после перезапуска; при смене модели полная история также
передаётся новой модели. Параметр N не применяется. По умолчанию по-прежнему
выбран Sliding Window.

### Sliding Window

В модель передаются только последние N сообщений и новый запрос. Более старые
сообщения остаются в локальном JSON для отображения, но полностью исключаются
из контекста модели. Дополнительных вызовов API нет.

### Sticky Facts / Key-Value Memory

Перед каждым основным ответом агент отдельным вызовом обновляет JSON-объект
`facts`. В нём сохраняются цель, ограничения, предпочтения, решения и
договорённости. Основной запрос получает developer-блок с актуальными facts и
последние N сообщений. Facts сохраняются отдельно в `history.json` и видны в
левой панели. Токены вызовов обновления памяти включены в общие метрики.

### Branching

После общей части диалога кнопка «Создать checkpoint и 2 ветки» клонирует
текущий транскрипт и `response_id` в «Ветку A» и «Ветку B». Дальнейшие ответы,
история веток независима; подтверждённые слои памяти общие для текущей задачи. Переключатель в левой панели мгновенно
восстанавливает выбранную ветку; обе ветки сохраняются между перезапусками.

### Сценарий сравнения на 12 сообщениях

Используйте одинаковое N, например 4, и трижды пройдите один сценарий сбора ТЗ:

1. Зафиксируйте цель продукта, аудиторию, платформу и срок.
2. Добавьте ограничения по бюджету, безопасности и интеграциям.
3. Обсудите два варианта архитектуры и выберите один.
4. Добавьте несколько второстепенных уточнений, чтобы ранние факты вышли из окна.
5. Попросите составить итоговое ТЗ со всеми исходными ограничениями.
6. Для Branching создайте checkpoint перед выбором архитектуры, рассмотрите
   разные варианты в A и B, затем сравните финальные ТЗ.

| Стратегия | Качество и стабильность | Токены | Удобство |
|---|---|---|---|
| Sliding Window | хорошо помнит недавнее, ранние детали теряются после выхода из N | минимальный расход | самая простая |
| Sticky Facts | стабильно сохраняет важные ранние факты, но зависит от качества извлечения | окно меньше, но есть дополнительный вызов facts | facts видны и проверяемы |
| Branching | каждая версия решения последовательна и не загрязняет соседнюю | расход считается отдельно в каждой ветке | удобно сравнивать альтернативы |

Автоматические тесты проверяют ограничение окна, обновление facts после каждого
сообщения, независимость веток и восстановление всех стратегий после
перезапуска. Для чистого ручного сравнения начинайте новый диалог перед каждой
стратегией.

Если расчётный вход превышает лимит выбранной модели, интерфейс показывает
жёлтое предупреждение, но агент всё равно отправляет запрос. При стандартной
стратегии Responses API модель может отклонить такой запрос с HTTP 400; ошибка
будет показана рядом с предупреждением. Неуспешный ход в историю не записывается.

## Проверка роста токенов

- **Короткий диалог:** отправьте 2–3 коротких вопроса и сравните поля «запрос»,
  «история», «ответ» и «диалог».
- **Длинный диалог:** продолжайте один диалог; «история», доля контекста,
  накопленные токены и стоимость будут расти.
- **Переполнение:** автоматический тест использует вход 300 000 токенов при
  лимите 272 000 и проверяет, что предупреждение появляется, но LLM всё равно
  вызывается:

```sh
go test ./internal/agent -run TestAgentComparesShortLongAndOverflowDialogs -v
go test ./internal/agent -run 'TestSlidingWindow|TestStickyFacts|TestBranching' -v
```

## Проверка

```sh
go test ./...
go vet ./...
go build -o bin/codex-chat ./cmd/codex-chat
```

Тесты используют фальшивый API-клиент или локальный тестовый HTTP-сервер и не
требуют настоящего API-ключа. При сборке Docker-образа тесты запускаются
автоматически.

Для ручной проверки сохранения контекста:

1. Начните диалог, например сообщите агенту своё имя.
2. Остановите приложение (`Ctrl+C` или `docker compose down`).
3. Запустите его снова той же командой и откройте страницу в том же браузере.
4. Спросите имя: прежние сообщения появятся на странице, а агент продолжит
   разговор с сохранённым контекстом.

На вкладке «Задачи» можно создать задачу или открыть сохранённую. При переключении
восстанавливаются переписка, рабочая память, предложения памяти, стратегия и ветки.
Долговременная память общая для задач одного браузерного профиля: её изменение
будет учтено и после возвращения к другой задаче. Активная задача и список задач
сохраняются после перезапуска приложения.

Кнопка «Новый диалог» очищает переписку только активной задачи, сохраняя её рабочую
память. Другие задачи не затрагиваются. Текущая задача из предыдущей версии
подхватывается автоматически; задачи, удалённые старой версией при создании новых,
восстановить нельзя.
