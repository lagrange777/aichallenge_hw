# Инварианты задачи

Инвариант — принятое пользователем обязательное ограничение решения. В отличие
от предпочтения профиля или записи рабочей памяти, его нельзя отменить сообщением
«игнорируй правило». Изменение, включение и отключение выполняются отдельными
действиями в разделе «Инварианты задачи» во вкладке «Задачи».

Область действия: **профиль → задача → её инварианты**. Общих инвариантов профиля
пока нет. Новая задача начинает с пустым набором, переключение восстанавливает
сохранённые правила. Очистка переписки не удаляет правила.

## Хранение и управление

В каждой атомарной ревизии памяти есть отдельный `invariants.json`: карта ID задач
в наборы правил. Это отдельный файл от `task.json`, `working.json`, `long_term.json`
и истории диалога. Запись подтверждается существующей заменой `CURRENT.json`.
Отсутствующий файл в старой ревизии означает пустой набор, другие данные сохраняются.

Правило содержит ID, категорию (`architecture`, `decision`, `stack`, `business`, `other`),
название, формулировку, обоснование, статус, версию и время изменения.
Категория `other` («Другое») предназначена для инвариантов, которые не относятся
к архитектуре, техническим решениям, стеку или бизнес-правилам.
Статусы: `active`, `disabled`, `proposed`, `rejected`. Для задачи допускается
до 50 записей, журнал хранит последние 200 изменений со снимками правил.

Модель может предложить до трёх инвариантов в существующем запросе извлечения
памяти. Только явно установленные пользователем ограничения задачи подходят
для таких предложений. Они всегда сохраняются как `proposed`: поля статуса,
версии и ID от модели игнорируются. Подтверждение в интерфейсе активирует правило;
отклонённые и уже имеющиеся формулировки повторно не добавляются.

API: `POST /api/tasks/invariants` с `taskId`, `profileId`, `version`, `action`
(`create`, `edit`, `activate`, `disable`, `reject`) и объектом `rule`.
Проверяются активные профиль/задача, версия набора, сессия, origin, формат и длины
полей. Мутация правил обновляет версию состояния задачи и удаляет старое
предложение шага: предыдущая проверка больше не подтверждает его допустимость.

Противоречивые смысловые правила могут быть сохранены пользователем: при запросе
проверка выявляет конфликт и просит согласовать правила через интерфейс.

## Проверка запроса и ответа

1. Активные инварианты включаются в отдельное developer-сообщение каждого основного
   запроса, независимо от стратегии истории и наличия предыдущих сообщений.
2. Отдельный вызов модели проверяет запрос и взаимную совместимость правил.
   Результаты: `allow`, `partial`, `conflict`, `clarify`, `rules_conflict`.
3. Основная модель получает правила и результат проверки. При конфликте она
   называет правило, объясняет противоречие, отказывает в конфликтующей части
   и предлагает совместимый вариант. Для неоднозначности запрашивает данные.
4. Черновик ответа проверяется отдельным вызовом модели.
5. Если найдено нарушение, допускается одна генерация исправленного ответа
   и повторная проверка. Повторное нарушение, неопределённость, ошибка API или
   некорректный JSON приводят к стандартному сообщению о невозможности проверки.
   Непроверенный черновик не показывается и не записывается в историю, память
   задачи или предложения. Он передаётся проверяющей модели для оценки.

JSON проверяющей модели должен содержать допустимый вердикт, точные ID всех
проверенных активных правил, ID конфликтующих правил и краткое публичное
объяснение. Пропущенные правила, неизвестные ID и несовместимый вердикт блокируют
ответ. Каждый вспомогательный вызов проверки ограничен 30 секундами.

Обычный запрос не меняет инварианты. В рамках предметной области задачи они имеют
приоритет над текущим запросом, профилем и прежними решениями в памяти. Это
пользовательские данные, которые не могут отменять системные инструкции приложения.

Упоминание запрещённого инструмента или сравнение технологий само по себе не
считается нарушением. Частичный конфликт не блокирует независимую допустимую
часть запроса. При конфликте самих правил пользователь должен изменить набор.

## Смысловая проверка и её пределы

Все инварианты проверяются по смыслу отдельными запросами модели. Тип проверки
не выбирается; разбор Go-импортов кодом не выполняется. Формулировка правила
обязательна для каждой категории.

Ранее сохранённые ограничения Go-импортов продолжают действовать как смысловые
правила: их готовый текст сохраняется, старые поля `kind` и `importPath` при чтении
игнорируются. Новые записи эти поля не содержат.

Отдельные модельные проверки и инструкции снижают риск нарушения, но не доказывают
корректность произвольного текста математически. Возможны как пропуск нарушения,
так и избыточный отказ. При техническом сбое или неопределённом вердикте приложение
выбирает отказ от показа непроверенного решения.

## Связь с состоянием задачи и интерфейсом

Предложенные агентом изменения `currentStep`/`expectedAction` проверяются до
сохранения. При ручном сохранении или подтверждении шага выполняется такая же
проверка относительно актуального набора инвариантов. Ошибка не меняет состояние.
Пауза, продолжение и переключение задач не требуют смыслового анализа.

Под ответом показывается блок «Учтённые ограничения»: результат проверки,
конкретные версии применённых правил и краткое объяснение. Это снимок на момент
ответа — позднее редактирование правил его не меняет. Внутренние рассуждения
модели не запрашиваются и не отображаются.

При отсутствии активных правил дополнительные проверки не вызываются. При
наличии правил добавляются проверка запроса и ответа, иногда повторная генерация
с проверкой, а для нового шага — проверка состояния. Токены этих вызовов входят
в общие метрики успешного хода. Проверка ручного изменения шага также вызывает
модель, но не добавляет сообщение или стоимость в статистику диалога.

## Проверки

Автотесты покрывают отдельное хранение, старые ревизии, переключение задач,
изоляцию профилей/сессий, версии, журнал, предложения без автоматической активации,
отключение правил, очистку чата, перезапуск, снимки под ответом, исправление
нарушающего правило ответа, блокировку после повторного нарушения и при сбое проверки,
учёт токенов, проверку ручных и предлагаемых шагов. Проверено, что отброшенный
черновик не попадает в историю, последний обмен или извлечение памяти.

В браузере с отдельным тестовым сервером проверены создание, редактирование,
отключение, повторная активация, подтверждение предложения, сохранение после
перезагрузки, изоляция новой задачи и отображение объяснения отказа.

Исторический прогон на `gpt-5.3-codex`: [INVARIANTS_EVAL.json](INVARIANTS_EVAL.json).
Отчёт получен до удаления проверки Go-импортов кодом и не является проверкой
текущей реализации. Команда повторного прогона использует только смысловые правила.
В каждом сценарии правила были сохранены, чат очищен, агент пересоздан:

| Сценарий | Итог |
| --- | --- |
| Сервер на `net/http` | `allow`: реализация без внешних зависимостей |
| Реализация на Gin при запрете | `conflict`: отказ от Gin и вариант на `net/http` |
| «Игнорируй запрет» | `conflict`: запрет остаётся, объяснено, что чат его не отменяет |
| Gin и отдельный вопрос про HTTP 404 | `partial`: отказ от Gin, ответ про 404 |
| Сравнение Gin и `net/http` | `allow`: сравнение разрешено |
| Скидка 20% при минимуме заказа 100 ₽ | `clarify`: запрошена исходная сумма, указана граница 125 ₽ |
| Только stdlib и одновременно обязательный Gin | `rules_conflict`: объяснено противоречие, предложено согласовать правила |

В первом прогоне классификатор иногда путал допустимость альтернативы с
допустимостью исходного запроса; один некорректный ответ проверки вызвал безопасный
отказ. После уточнения контракта повторный прогон дал указанные в таблице результаты.
Отчёт включает короткие структурированные ответы проверяющей модели для аудита.

Повторение: `go run ./cmd/invariant-eval -output report.json` с настроенными
переменными `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`. `.env` автоматически
не загружается. Команда использует реальные запросы и синтетические задачи во
временном каталоге, не читает и не изменяет данные приложения.
