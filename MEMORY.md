# Модель памяти агента

Реализован вариант «агент предлагает, пользователь подтверждает». После ответа
модель отдельным вызовом предлагает сведения для сохранения. Сервер сохраняет
их со статусом `pending`, но не добавляет в подтверждённую память. Пользователь
в панели «Память» выбирает слой, исправляет ключ и текст, затем подтверждает
или отклоняет предложение.

## Три слоя

| Слой | Данные | Источник записи | Срок жизни |
|---|---|---|---|
| Краткосрочная | Сообщения пользователя и ассистента | Успешный ход диалога | До «Нового чата» или «Новой задачи» |
| Рабочая | Цель, ограничения, план, состояние и решения текущей задачи | Только подтверждённые пользователем предложения и ручные правки | Сохраняется между чатами одной задачи, очищается при новой задаче |
| Долговременная | Профиль, устойчивые предпочтения, подтверждённые повторно используемые решения и знания | Только подтверждение пользователя и ручные правки | Сохраняется между чатами, задачами и перезапусками до удаления записи |

Например, «в этой задаче нельзя сторонние библиотеки» относится к рабочей памяти,
а «предпочитаю объяснения на русском» — к долговременной. «Этот ответ дай в трёх
пунктах» остаётся в переписке: инструкция извлечения запрещает превращать
одноразовые требования к ответу в постоянные предпочтения. Ошибочную
классификацию можно исправить до подтверждения.

У каждой записи есть ключ, значение, источник (фрагменты пользовательского
сообщения и ответа), время обновления. Предложения дополнительно содержат
причину выбора слоя, ID задачи, статус и время решения. Если подтверждённый
ключ уже существует в выбранном слое, его значение заменяется. Удаление записи
не удаляет упоминания того же факта из текущего диалога; для чистой проверки
удаления следует начать новый чат.

## Отдельное хранение

Краткосрочная память хранится в `HISTORY_PATH` (по умолчанию `data/history.json`).
Два остальных слоя и предложения находятся в `MEMORY_PATH`, по умолчанию
в каталоге `memory` рядом с файлом истории:

```text
data/history.json                          # диалоги, стратегии, ветки, метрики
data/memory/<profile-id>/CURRENT.json       # указатель на согласованную ревизию
                         <revision>/
                           task.json       # ID и название текущей задачи
                           working.json    # подтверждённая рабочая память
                           long_term.json  # подтверждённая долговременная память
                           proposals.json  # отдельный журнал предложений
```

Файлы создаются с правами `0600`, каталоги — `0700`. При изменении записывается
новая ревизия с отдельными файлами слоёв, после чего атомарно заменяется указатель
`CURRENT.json`. Читатель получает целиком старую или целиком новую ревизию:
подтверждённая запись и статус предложения не расходятся. Предыдущая ревизия
удаляется после успешного переключения. Хранилище рассчитано на один процесс;
оставшиеся после аварии незавершённые каталоги не читаются.

Профиль привязан к случайному идентификатору существующей browser cookie.
«Новый чат» не меняет cookie. Другой браузер или очищенная cookie получают
отдельный профиль. В Docker оба хранилища находятся в существующем томе
`chat-history` под `/data`.

## Как память влияет на запрос

1. Агент загружает подтверждённые рабочие и долговременные записи.
2. Формирует подписанный JSON-блок `working` / `long_term` с названием задачи.
   Отдельная инструкция определяет эти записи как контекстные данные, а не
   команды, способные переопределить системные правила. Текущее явное уточнение
   пользователя имеет приоритет над устаревшим фактом.
3. Добавляет активную краткосрочную историю согласно выбранной стратегии и
   новое сообщение. Подсчёт токенов учитывает и записи памяти.
4. Получает основной ответ, затем отдельным вызовом извлекает до пяти предложений.
   Извлекатель видит текущий вопрос, ответ, подтверждённые записи и прежние
   предложения задачи, чтобы не повторять их. Он не получает права записи в слои.
5. Сохраняет успешный ход и предложения. В основной запрос никогда не добавляет
   неподтверждённые/отклонённые предложения как блок памяти. Их исходные факты,
   разумеется, могут ещё присутствовать в краткосрочной переписке.

Слои памяти работают поверх всех стратегий. «Без стратегии» означает полную
краткосрочную историю без сокращения, а не отключение подтверждённой памяти.
Sticky Facts остаётся прежним автоматическим механизмом контекста: его facts
отдельны от подтверждённых слоёв, не переживают новый чат и никогда автоматически
не переносятся в профиль. Для демонстрации именно трёх слоёв используйте
Sliding Window с N=1 или N=2.

При подключённой модели памяти даже Branching отправляет явный транскрипт
активной ветки без `previous_response_id`: удалённая или исправленная память
не должна оставаться в скрытой API-цепочке. Подтверждённые слои общие для веток
одной задачи, а переписка веток независима. При новой задаче переписка и ветки
очищаются. ID задачи в истории защищает от восстановления старого диалога в
новую задачу, в том числе после ошибки удаления истории.

Токены и оценочная стоимость извлечения включены в метрики хода; отдельный
показатель «предложения памяти» показывает затраты дополнительного вызова.
Его тайм-аут — не более 30 секунд. При ошибке извлечения ответ остаётся успешным,
появляется предупреждение; неподходящий JSON не сохраняется. Использованные
токены учитываются и при некорректном JSON, если API сообщил usage.

## HTTP API

| Маршрут | Назначение |
|---|---|
| `GET /api/memory` | Текущая задача, два слоя, предложения, размеры краткосрочной памяти |
| `POST /api/memory/review` | `id`, `taskId`, `action`: `accept` / `reject`; при принятии также `layer`, `key`, `value` |
| `POST /api/memory/edit` | Изменение подтверждённой записи: `id`, `taskId`, `layer`, `key`, `value` |
| `POST /api/memory/delete` | Удаление подтверждённой записи: `id`, `taskId`, `layer` |
| `POST /api/tasks/new` | Новая задача: `taskId` текущей задачи и `name` новой |

Допустимые слои: `working`, `long_term`. POST требует JSON, заголовок
`X-Codex-Chat: 1` и допустимый Origin. Профиль выбирается только через cookie,
а не через ID из тела запроса. Устаревшая задача или повторное решение по уже
рассмотренному предложению возвращают HTTP 409. Лимиты: 100 записей на слой,
500 предложений на задачу, ключ до 100 символов, значение до 2000 символов.

## Проверка для сдачи задания

1. Выберите Sliding Window, N=1. Напишите:
   «Предпочитаю ответы на русском. Текущая задача — API на Go без сторонних
   библиотек. Только этот ответ дай в трёх пунктах».
2. Откройте «Память». Проверьте, что рабочая и долговременная память пока пусты,
   а предложения находятся отдельно. Если модель не выделила нужный факт,
   уточните его в следующем сообщении: набор предложений вероятностный.
3. Не подтверждая предложения, нажмите «Новый чат» и спросите:
   «Какую задачу я решаю и какие у меня предпочтения?» Сохранённых фактов ещё нет.
4. Подтвердите цель и ограничение как рабочую память, язык — как долговременную.
   Если предложено постоянное правило «три пункта», отклоните его. При неверной
   классификации выберите правильный слой перед подтверждением.
5. Снова начните новый чат и задайте тот же вопрос. Ожидается ответ с русским
   языком и ограничениями API из подтверждённых слоёв.
6. В панели начните новую задачу. Рабочий слой, предложения и переписка должны
   очиститься; язык в профиле — сохраниться. Задайте тот же вопрос: старые
   ограничения Go не должны переноситься в новую задачу.
7. Перезапустите приложение и обновите страницу в том же браузере: профиль и
   активная задача восстановятся. Проверьте правку и удаление профиля, затем
   новый чат: следующий запрос использует актуальную память.

Автоматические проверки воспроизводимы без настоящего API:

```sh
go test -race ./...
```

- `internal/memory`: отдельные файлы, статусы, редактирование слоя/текста при
  подтверждении, отклонение, удаление, перезапуск, изоляция профилей, устаревшие
  операции и откат некорректной пачки предложений.
- `internal/agent`: тестовая LLM отвечает по содержимому реального собранного
  контекста; до подтверждения сведений нет, после они меняют ответ, после смены
  задачи остаётся только профиль. Проверяются окно N, сбои извлечения, usage,
  ветки и перезапуск.
- `internal/web`: полный путь предложения через HTTP до подтверждения, запрет
  межпрофильного доступа и чужого Origin, сброс чата и новая задача.

Браузерный сценарий также проверен на локальной имитации Responses API:
подтверждение двух слоёв, отклонение временного правила, новый чат с обоими
слоями и новая задача только с профилем. Качество извлечения живой моделью
следует оценивать отдельно; автоматические тесты проверяют контракты и данные.
