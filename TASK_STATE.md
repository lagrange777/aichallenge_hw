# Состояние задачи

Задача — сохраняемая единица работы внутри профиля: название, переписка,
рабочая память и теперь конечный автомат. У каждой задачи своё состояние;
смена профиля или задачи восстанавливает именно её точку продолжения.

## Автомат и подтверждения

```text
planning → execution → validation → done
                ↑           |
                └───────────┘
                 исправления
```

`planning` — согласование цели и плана; `execution` — выполнение текущего
шага; `validation` — проверка результата; `done` — терминальное состояние.
Можно обновлять точку продолжения внутри активного этапа. Прямой переход
из планирования к проверке или завершению запрещён сервером.

При переходе в `validation` нужен непустой результат выполнения. Для `done`
также нужен итог проверки. Сам по себе текст «готово» ничего не меняет:
пользователь проверяет предложенный результат и подтверждает завершение.
Проверка содержательности доказательств остаётся за пользователем: чат
не имеет инструментов запуска кода. Модель получает указание отличать
концептуальную проверку от тестов, действительно выполненных пользователем.
Для новой работы после `done` создаётся новая задача.

Пауза — флаг `paused`, ортогональный этапу. Она доступна на каждом из трёх
рабочих этапов между ответами. Текущий запрос не прерывается. На паузе сервер
отклоняет новые сообщения до вызова модели, включая вспомогательные запросы.
Подтверждение и ручное изменение точки продолжения также недоступны на паузе.
Отклонить предложение, смотреть память и переключать задачи можно.

## Что сохраняется

`Task.workflow` хранится в `task.json`; у неактивных задач — вместе с ними в
`tasks.json`. Используется существующая атомарная запись ревизии памяти через
`CURRENT.json`. Переписка остаётся в своём хранилище.

| Поле | Назначение |
| --- | --- |
| `stage`, `paused` | Этап и пауза |
| `goal` | Цель и критерии готовности |
| `currentStep` | Конкретный текущий шаг |
| `expectedActor`, `expectedAction` | Кто действует (`user`/`agent`) и что делает |
| `completed`, `result` | Выполненное, решения и промежуточный результат |
| `openQuestions`, `validation` | Нерешённые вопросы и итог проверки |
| `proposal` | Неподтверждённое предложение модели, отдельно от принятого состояния |
| `lastTurn` | Последний успешный обмен для продолжения до подтверждения предложения |
| `version` | Проверка устаревших запросов из других вкладок |
| `events` | Последние 200 действий: переходы, паузы, подтверждения и отклонения |

Старые задачи автоматически получают `planning` и начальный шаг: прогресс не
угадывается по переписке. Их ID, память и история сохраняются.

Модель предлагает полный обновлённый checkpoint в существующем вспомогательном
запросе извлечения памяти — дополнительного вызова API не добавлено. Предложение
проверяется сервером, но не применяется без пользователя. Новый успешный ответ
заменяет предыдущее предложение; ручное сохранение или подтверждение очищает его.

`lastTurn` обновляется автоматически после успешного ответа, даже если извлечение
предложений вернуло ошибку. Лимиты — 6000 символов пользовательского сообщения и
12000 символов ответа, с явной отметкой сокращения. Полный текст остаётся в истории.
Этот обмен — контекст разговора, а не подтверждённое выполнение внешних действий.
Для надёжного продолжения долгих задач нужно подтверждать или вручную поддерживать
накопленные результаты: один последний обмен не заменяет всю историю.

При ошибке сохранения checkpoint ответ остаётся в диалоге и возвращается
предупреждение. История диалога и хранилище памяти не составляют одну транзакцию.

## Контекст и интерфейс

Каждый основной запрос получает профиль, рабочую и долговременную память,
подтверждённое состояние и последний обмен. Предложение и журнал переходов
не попадают в контекст ответа. Состояние добавляется независимо от стратегии
сжатия истории и сохраняется после «Нового чата».

Во вкладке «Задачи» есть полоса этапов, точка продолжения, предложение с кнопками
подтверждения/отклонения, ручное редактирование и история изменений. В чате видны
этап, пауза и наличие предложения. На паузе и после завершения отправка отключена.

«Продолжить» снимает паузу. Если действует агент, «Выполнить текущий шаг» отправляет
запрос продолжения с сохранённым контекстом. Если нужны данные пользователя,
«Ответить агенту» открывает чат. Существующий черновик сообщения сохраняется.

API: `POST /api/tasks/state`, поля `taskId`, `profileId`, `version`, `action`
(`save`, `accept`, `reject`, `pause`, `resume`), `progress` для ручного сохранения.
Проверяются сессия, активный профиль, задача, версия, допустимый переход и размеры
полей. Чат из интерфейса также передаёт `taskId` и `taskVersion`.

## Проверки

Автоматические тесты покрывают:

- паузу, перезапуск, переключение задач и продолжение на каждом рабочем этапе;
- обратный переход к исправлениям и терминальность `done`;
- недопустимые переходы, отсутствие результата/проверки и устаревшие версии;
- предложение без автоматического применения, подтверждение и отклонение;
- миграцию активной и сохранённых задач без состояния;
- продолжение после очистки чата с текущим шагом и выполненной работой в контексте;
- отсутствие вызовов модели на паузе и после завершения;
- сохранение последнего обмена при сбое извлечения;
- изоляцию HTTP-сессий/профилей и отклонение запросов с чужого сайта.

`go test -race ./...` и `go vet ./...` проходят. Браузерная проверка использует
отдельный сервер с имитацией модели и отдельные данные: получение предложения,
подтверждение, пауза, перезагрузка страницы и продолжение кнопкой.
Проверки ответов здесь детерминированные: подтверждают передачу состояния в модель,
но не гарантируют поведение каждой реальной LLM.

Реальная проверка на `gpt-5.3-codex` сохранена в [TASK_STATE_EVAL.json](TASK_STATE_EVAL.json).
Во всех трёх случаях задача была приостановлена, агент пересоздан, запрос на паузе
отклонён, затем после снятия паузы отправлено одно и то же «Продолжи» без переписки:

| Сохранённый этап | Ответ модели | Предложенный следующий этап |
| --- | --- | --- |
| planning | План валидатора, ожидание подтверждения перед кодом | execution |
| execution | Реализация Go-функции по сохранённым правилам | validation |
| validation | Найден пропуск проверки символов, предложено исправление без выдачи нового кода | execution |

В повторном прогоне модель не запрашивала заново сохранённые требования,
не заявляла запуск тестов и предложила допустимые переходы. В первом прогоне
она сразу выдала исправленный код на этапе проверки; инструкции были уточнены,
чтобы до подтверждения обратного перехода ограничиваться описанием дефекта.
Это наблюдение конкретного прогона, а не гарантия поведения всех моделей.

Повторить проверку можно командой `go run ./cmd/task-state-eval -output report.json`
с настроенными переменными `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`.
Команда делает реальные платные запросы на синтетических примерах; данные
приложения не читает и не меняет. Файл `.env` автоматически не загружается.
