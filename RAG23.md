# Задание 23: реранкинг, фильтрация и query rewrite

Продолжение локальной индексации и первого RAG-запроса. Используется существующий SQLite-индекс `artifacts/docindex/index.sqlite`, стратегия `structured`. Переиндексация не нужна.

## Режимы

| Режим | Поиск | Второй этап |
|---|---|---|
| `baseline` | исходный вопрос | первые K после поиска |
| `filter` | исходный вопрос | LLM-реранкинг и порог |
| `rewrite` | исходный + переписанный вопрос | объединение RRF, первые K |
| `full` | исходный + переписанный вопрос | объединение RRF, LLM-реранкинг и порог |

Rewrite создаёт поисковую формулировку, сохраняя смысл, отрицания, числа и идентификаторы. Проверяются JSON, длина, сохранение латинских идентификаторов/чисел и отсутствие новых чисел. Семантическая эквивалентность не гарантируется этой проверкой. При ошибке используется исходный вопрос с явным предупреждением.

Для каждого запроса извлекается до **20** чанков. Дубликаты объединяются по `chunk_id`, используется reciprocal rank fusion `Σ 1/(60 + rank)`, затем остаются лучшие 20 кандидатов. При равенстве — исходный ранг, затем ID. При одном запросе сохраняется исходный порядок. Cosine в диагностике относится к первому поиску, где встретился чанк; он не смешивается с оценкой реранкера.

Реранкер оценивает одним запросом все кандидаты относительно **исходного вопроса**:

- **0** — не относится к вопросу;
- **1** — общая тема, но нет полезного доказательства;
- **2** — частичное полезное доказательство;
- **3** — прямое доказательство для ответа.

Для 2–3 реранкер выбирает номер непустой строки-доказательства из чанка; сервер сам извлекает дословную цитату из исходного текста. Это исключает ошибки копирования отступов и пробелов в коде. Сервер проверяет полный набор ID без повторов, диапазон баллов и допустимость строки. После сортировки по оценке, при равенстве по поисковому рангу, применяются порог и **K после = 5**. Контекст ограничен 9000 Unicode-символами; последний чанк может быть обрезан. Сохраняется именно переданный модели текст.

Валидация цитаты подтверждает её происхождение, но не доказывает правильность оценки. Поэтому результаты дополнительно проверяются по смыслу. Для некорректного ответа реранкера допускается одно исправление с обратной связью валидатора; обе попытки учитываются в токенах и времени, предупреждение сохраняется в трассе. Повторная ошибка завершает запрос явно. Если все кандидаты отсеяны, агент отвечает о недостатке данных без вызова модели ответа. Отброшенные чанки не возвращаются в контекст.

Настройки на один запрос: `mode`, `topKBefore` (1–20), `topKAfter` (1–10, не больше первого), `relevanceThreshold` (0–3). Значения по умолчанию API: `baseline`, 20, 5, 2. Веб-интерфейс предлагает `full`; во вкладке RAG загружает выбранный калибровкой порог.

## Веб-интерфейс

Во вкладке **RAG** доступны сводка четырёх режимов, калибровка, 15 вопросов с ожиданиями, выбор двух режимов для сопоставления и независимый интерактивный запрос. Под каждым ответом видны переписанный запрос, переданные источники, оценки/цитаты/причины отсева всех кандидатов и использование вспомогательных моделей.

В обычном чате включите **Использовать RAG**, раскройте **Настройки RAG** и выберите режим. Настройки передаются с каждым сообщением и не меняют общий retriever. Вспомогательные запросы используют серверную модель по умолчанию, а ответ — модель, выбранную в чате; фактическая модель каждого этапа сохраняется в диагностике. В эксперименте и независимом запросе все этапы используют одну выбранную модель.

`GET /api/rag/experiment` возвращает сохранённый отчёт (`RAG_EXPERIMENT_PATH`). `POST /api/rag/run` выполняет один режим в новой сессии, без изменения истории и отчёта:

```json
{"query":"Когда удаляется неактивная сессия?","model":"gpt-5.3-codex","options":{"mode":"full","topKBefore":20,"topKAfter":5,"relevanceThreshold":2}}
```

Оба API требуют заголовок `X-Codex-Chat: 1`, проверяют Origin; POST также требует `Content-Type: application/json`. Ошибочные параметры отклоняются до платных вызовов.

## Воспроизведение эксперимента

Команды `calibrate` и `compare` выполняют платные запросы OpenAI и отправляют вопросы/фрагменты корпуса. Ключ читается из окружения или из явно заданного файла; в отчёт не записывается.

```bash
go run ./cmd/rag-bench -phase calibrate -env-file .env -out artifacts/rag23-new
go run ./cmd/rag-bench -phase compare -env-file .env -out artifacts/rag23-new
# Продолжить после ошибки, не повторяя сохранённые режимы:
go run ./cmd/rag-bench -phase compare -env-file .env -out artifacts/rag23-new -resume
# Применить оценки именно этих ответов (проверяется SHA-256):
go run ./cmd/rag-bench -phase review -out artifacts/rag23-new -reviews artifacts/rag23-new/reviews.json
```

В Docker доступен `/rag-bench`; укажите `-index /documents/artifacts/index.sqlite`, `-questions /documents/rag23-questions.json`, `-calibration-questions /documents/rag23-calibration.json` и записываемый `-out /data/rag23`. Для отображения нового отчёта задайте `RAG_EXPERIMENT_PATH=/data/rag23/comparison.json`.

Калибровка: 6 отдельных вопросов в `documents/rag23-calibration.json`, четыре ответимых и два без ответа. На одних и тех же оценках проверяются пороги 1/2/3. Максимизируется сумма попаданий эталонного фрагмента и пустых выборок для неответимых вопросов; при равенстве выбирается порог, ближайший к 2. Правило задано до прогона.

Итоговый набор `documents/rag23-questions.json`: 10 исходных вопросов задания 22, две переформулировки и три вопроса без запрошенных данных. Пересечение ID/формулировок с калибровкой запрещено. Ожидания и эталонные цитаты используются только для оценки, не передаются переписывателю, реранкеру или модели ответа.

Все 60 ответов получаются в независимых сессиях с одинаковой моделью и инструкцией, без профилей, памяти, MCP и истории. Temperature — значение API по умолчанию. Один прогон не устраняет стохастическую вариативность; rewrite в двух режимах также генерируется независимо. Сравнение показывает наблюдение на небольшом корпусе, а не универсальное преимущество метода.

Метрики: смысловая корректность/полнота 0–2, галлюцинации, воздержания, поддержка ссылок; отдельно попадание точной эталонной цитаты до/после обработки, число источников, время и токены. Попадание цитаты — узкая retrieval-метрика, не замена оценке ответа. Для неответимых вопросов полезное воздержание/обоснованное исправление ложной предпосылки получает 2/2. Оценки выполняет Codex с пояснениями, без независимого второго оценщика. LLM-токены включают rewrite и reranker; embedding-токены хранятся отдельно.

Артефакты: `calibration.json` с исходными оценками, `comparison.json` с полными трассами, `comparison.md` с ответами, `reviews.json` с привязанными к ответам оценками. Запуск не перезаписывает существующую калибровку; продолжение сверяет хеши корпуса/датасета, модель, настройки и инструкции.

## Проверки

`go test ./...`, `go vet ./...`, `go test -race ./internal/agent ./internal/rag ./internal/web`. Тесты покрывают RRF/дедупликацию, пороги и top-K, неподтверждённые цитаты/ID, rewrite fallback, пустой контекст без вызова LLM, учёт вспомогательных токенов, независимость данных и валидацию API до внешних запросов.

## Результат реального прогона

Модель `gpt-5.3-codex`, 15 вопросов × 4 режима. Порог **2/3** выбран до итогового прогона. На калибровке пороги 1/2/3 дали соответственно 3/3/3 попадания из четырёх ответимых вопросов и 0/2/2 пустые выборки из двух неответимых; при равенстве выбран заранее предпочитаемый порог 2.

| Режим | Корректность /2 | Полнота /2 | Эталон в контексте /12 | Источников, среднее | LLM-токены, всего | Время, среднее |
|---|---:|---:|---:|---:|---:|---:|
| baseline | 1,73 | 1,73 | 9 | 5,00 | 31 244 | 2,82 с |
| filter | 1,93 | 1,80 | 11 | 2,60 | 171 558 | 15,24 с |
| rewrite | 1,73 | 1,73 | 9 | 5,00 | 35 299 | 4,25 с |
| full | 1,93 | 1,80 | 11 | 2,87 | 170 377 | 16,39 с |

- **q02:** baseline и rewrite не находят срок; filter/full поднимают раздел `internal/web` и отвечают «12 часов». Сохранение истории на диске в ответе не раскрыто, поэтому полнота 1/2.
- **q04:** исходный поиск уже давал правильный ответ по эквивалентному месту README, хотя точная эталонная цитата отсутствовала. Реранкинг улучшает здесь retrieval-метрику, а не смысловой результат.
- **p01:** разговорная переформулировка про неактивную сессию не находит нужный фрагмент даже в 20 кандидатах. Все режимы дают частичный ответ про диск и признают отсутствие срока RAM. Реранкер не восстанавливает документ, отсутствующий в кандидатах.
- **n02:** filter/full отсекают все чанки и возвращают стандартное сообщение без модели ответа. Baseline/rewrite тоже не выдумывают SLA, но необоснованно заявляют об отсутствии информации о самом проекте; за эту лишнюю формулировку корректность снижена до 1/2. Это смысловая оценка одного оценщика, а не автоматический факт.
- Для ложных предпосылок n01/n03 полезен и ответ с доказательствами файлового хранения. Поэтому пустая выборка сама по себе не означает лучший ответ: filter даёт две пустые выборки из трёх отрицательных вопросов, full — одну, но оба режима корректно обрабатывают все три.

На этом наборе основную пользу дал реранкинг. Rewrite отдельно не повысил оценки; full не превзошёл filter и работает медленнее. За сокращение контекста приходится платить дополнительным LLM-запросом на оценку 20 кандидатов: суммарные LLM-токены выросли примерно в 5,5 раза. Практический выбор для этого корпуса — `filter`, оставляя `full` доступным для экспериментов. Настройка интерфейса `full` демонстрирует весь требуемый пайплайн.

Все итоговые вызовы прошли без fallback rewrite и без повторного исправления реранкера. Токены таблицы относятся к 60 завершённым результатам; калибровка, предварительные неудачные проверки формата цитат и запросы демонстрации в них не включены. Ожидания не передавались ни одному этапу генерации.
