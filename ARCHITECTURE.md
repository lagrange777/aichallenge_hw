# Архитектура Codex Chat CLI

Дата решения: 2026-08-31.

## Цель

Небольшое интерактивное CLI-приложение на Go принимает сообщения пользователя,
отправляет их в OpenAI Responses API и печатает текст ответа. Контекст диалога
живёт только во время текущего запуска приложения.

## Проверенные API-решения

- Использовать `POST /v1/responses`: OpenAI рекомендует Responses API для новых
  многоходовых и reasoning-сценариев.
- Использовать `gpt-5.3-codex` по умолчанию как актуальную специализированную
  Codex-модель из каталога. Модель не зашита жёстко в поведение приложения:
  переменная `OPENAI_MODEL` позволяет сменить её без перекомпиляции.
- Передавать `previous_response_id` после первого сообщения. Так OpenAI API
  связывает очередной запрос с предыдущим ответом, а клиенту не нужно каждый раз
  пересылать полный диалог.
- Передавать `instructions` в каждом запросе: при использовании
  `previous_response_id` инструкции предыдущего ответа автоматически не
  наследуются.
- Читать ключ только из `OPENAI_API_KEY`. Ключ не хранится в исходниках,
  конфигурационных файлах или истории диалога.

Официальные источники:

- https://developers.openai.com/api/reference/cli/resources/responses/methods/create
- https://developers.openai.com/api/docs/models/gpt-5.3-codex
- https://developers.openai.com/api/docs/guides/latest-model

## Компоненты

```text
cmd/codex-chat/main.go
        │
        ├── internal/config     переменные окружения и значения по умолчанию
        ├── internal/cli        цикл чтения, команды и терминальный UI
        ├── internal/chat       состояние текущей сессии
        └── internal/openai     HTTP-клиент Responses API

Dockerfile                     сборка, тесты и минимальный runtime-образ
compose.yaml                   интерактивный запуск и runtime-конфигурация
```

### `internal/config`

Проверяет наличие `OPENAI_API_KEY`, читает `OPENAI_MODEL` и
`OPENAI_BASE_URL`. Последняя настройка нужна главным образом для тестирования и
совместимых API-шлюзов; по умолчанию используется `https://api.openai.com/v1`.

### `internal/openai`

Инкапсулирует HTTP-протокол и авторизацию. Публичный метод принимает текст,
необязательный ID предыдущего ответа и возвращает ID и итоговый текст нового
ответа. Реализация не зависит от сторонних библиотек, поэтому каркас имеет
минимальную поверхность зависимостей и использует стабильный REST-контракт.

### `internal/chat`

Хранит только `previous_response_id` текущего процесса. Обновляет его после
успешного ответа. Команда `/reset` очищает состояние и начинает новый диалог.
Транскрипт и API-ключ на диск не записываются.

### `internal/cli`

Поддерживает сообщения, продолжение строки через `\` и команды `/help`,
`/status`, `/clear`, `/new`, `/reset`, `/exit`. Терминальный UI показывает
стартовую карточку, prompt `›`, состояние выполнения и визуально отделённые
ответы. ANSI-цвет включается только при выводе в терминал и может быть отключён
через `NO_COLOR`. Управляющие символы в ответах модели и API-ошибках удаляются
перед выводом. Ошибка одного API-вызова не завершает сессию.

## Поток одного сообщения

1. CLI читает непустую строку или собирает несколько строк, отмеченных `\`.
2. Сессия передаёт строку и текущий `previous_response_id` API-клиенту.
3. Клиент вызывает `/v1/responses` с моделью, инструкциями и `store: true`.
4. Клиент собирает все блоки `output_text` из ответа.
5. Сессия сохраняет новый `response.id`, CLI печатает текст.

## Ошибки и безопасность

- До запуска чата приложение явно сообщает об отсутствии ключа.
- Неуспешные HTTP-ответы преобразуются в короткую ошибку с кодом и сообщением
  API; тело ограничивается по размеру.
- HTTP-клиент имеет тайм-аут, а основной контекст отменяется по SIGINT/SIGTERM.
- Секрет не логируется и не включается в ошибки.

## Границы первого каркаса

Первая версия синхронная и не стримит токены, не сохраняет историю между
запусками и не вызывает инструменты модели. Эти возможности можно добавить без
изменения CLI-контракта благодаря интерфейсу клиента и отдельному слою сессии.

## Контейнеризация

`Dockerfile` использует многоэтапную сборку: официальный Go-образ компилирует и
тестирует приложение, после чего в `scratch`-образ копируются только статический
бинарник и корневые TLS-сертификаты. Контейнер работает от непривилегированного
UID, с файловой системой только для чтения и без Linux capabilities.

Секрет передаётся только при запуске через `OPENAI_API_KEY`. `.dockerignore`
исключает `.env` и локальные артефакты из контекста сборки. `compose.yaml`
включает TTY и открытый stdin, необходимые для интерактивного чата.
