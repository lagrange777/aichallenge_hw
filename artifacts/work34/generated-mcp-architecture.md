# ADR: Архитектура подключения MCP в codex_chat_cli

- Статус: Предложено
- Дата: 2026-10-18

## Контекст

Проект использует MCP в двух разных ролях:

1. Подключение к внешним/локальным MCP-серверам для discovery инструментов и вызовов из чата.
2. Отдельный локальный MCP-сервер `project-mcp` для команды `/help` (чтение Git-ветки и публичного списка файлов проекта).

По коду это разделено на:

- MCP-клиент: `internal/mcpclient/client.go`
- MCP-сервер проекта: `internal/projectmcp/server.go`, точка входа `cmd/project-mcp/main.go`
- Встраивание в окружение: `compose.yaml`
- Использование в агенте `/help`: `internal/agent/project_help.go`

Отдельно важно, что в документации уже есть описание MCP как пользовательской функции, но нет отдельного ADR с фиксированным архитектурным решением и явными последствиями.

## Решение

### 1) Клиент MCP: короткие сессии, Streamable HTTP, жёсткая валидация

`internal/mcpclient/client.go` реализует подключение через официальный Go SDK (`mcp.StreamableClientTransport`) и явно задаёт ограничения:

- endpoint валидируется (`ValidateEndpoint`):
  - запрет логина в URL, query, fragment;
  - ограничение длины URL;
  - разрешён `https`, а `http` только для loopback/`localhost` и точных адресов из `MCP_HTTP_ENDPOINTS`.
- токен проверяется на отсутствие CR/LF;
- тайм-аут проверки и discovery — 30 секунд;
- редиректы отключены (`CheckRedirect -> http.ErrUseLastResponse`);
- тело ответа ограничивается 4 MiB;
- discovery проходит `initialize` + пагинацию `tools/list` с защитами:
  - максимум 100 страниц;
  - максимум 2000 инструментов;
  - защита от повторяющихся курсоров;
  - отклонение некорректного `tools/list` (пустые имена, дубли, отсутствующая schema).

Итог: соединение проектируется как **проверка/вызов с ограниченным временем жизни**, а не как бесконтрольный постоянный канал.

### 2) Разрешения на инструменты: не blanket-запрет записи, а набор точных условий

Функция `ChatToolAccess` в `internal/mcpclient/client.go` задаёт фактическую модель доступа для чата:

- `readOnlyHint=true` => инструмент разрешён без мутаций;
- для мутаций разрешение возможно **только** при одновременном выполнении условий:
  1. `(serverName, toolName)` входит в allowlist `chatMutationAllowed`;
  2. `OpenWorldHint` задан и равен `false` (closed-world);
  3. для `mock-issue-mcp`: `DestructiveHint` задан и равен `false`;
  4. для `demo-*` серверов: `DestructiveHint` должен быть явно задан (не `nil`).

Allowlist ограничен конкретными инструментами:

- `mock-issue-mcp`: `save_issue_report`
- `demo-order-mcp`: `create_buy_order`, `record_order_execution`, `record_validation_rejection`
- `demo-validation-mcp`: `validate_order`
- `demo-broker-mcp`: `execute_validated_order`

Следствие: проект не утверждает, что «все destructive-инструменты запрещены всегда»; вместо этого действует более нюансная комбинация аннотаций и жёсткого allowlist.

### 3) Локальный MCP-сервер проекта (`project-mcp`) как read-only источник контекста для `/help`

`internal/projectmcp/server.go` поднимает stateless Streamable HTTP endpoint `/mcp` и публикует только два инструмента:

- `git_branch` — текущая ветка/commit/detached;
- `project_files` — до 160 tracked публичных путей.

Оба инструмента размечены `ReadOnlyHint=true`, `IdempotentHint=true`, `OpenWorldHint=false`.

Ограничения и защита в реализации:

- на `/mcp` отклоняется любой запрос с `Origin` (403), допускаются программные клиенты;
- тело запроса ограничено 64 KiB;
- вызовы git идут с timeout 5 секунд;
- окружение git очищено от пользовательской конфигурации и интерактивных prompt;
- вывод git ограничен 1 MiB;
- `project_files` фильтрует пути: исключает скрытые сегменты и каталоги `data`, `artifacts`, `tools`, `documents`, оставляет только публичные расширения и фиксированные файлы (`go.mod`, `Dockerfile`).

### 4) Развёртывание: изоляция `project-mcp` в Compose

`compose.yaml` фиксирует архитектурный контракт:

- отдельный сервис `project-mcp` (цель сборки `project-mcp`);
- read-only контейнер, dropped capabilities, `no-new-privileges`;
- в контейнер монтируется только `./.git:/project/.git:ro` (без полного дерева проекта и без `.env`);
- основной сервис `codex-chat` обращается к `PROJECT_MCP_URL=http://project-mcp:8094/mcp`;
- этот endpoint отдельно разрешён в `MCP_HTTP_ENDPOINTS`.

Тем самым `/help` получает живые Git-метаданные и список публичных путей через MCP, но `project-mcp` не имеет доступа к пользовательским данным приложения.

### 5) Интеграция в `/help`

`internal/agent/project_help.go` фиксирует, что `/help` работает как evidence-only поток:

- команда ограничена вопросом до 4000 символов;
- ответ строится через retrieval контекста проекта;
- комментарий в коде явно запрещает в этом потоке запуск trading/scheduler инструментов, изменение task memory и повторное использование stale hidden API chain.

Это согласуется с ролью `project-mcp`: давать минимально необходимый живой контекст о состоянии репозитория, а не расширять права агента на запись.

## Последствия

### Положительные

- Снижение риска утечки/эскалации: строгая валидация endpoint и ограничение HTTP для доверенных локальных адресов.
- Предсказуемость discovery: лимиты на страницы/инструменты/размер ответа и тайм-ауты.
- Контролируемая модель разрешений: read-only по умолчанию + узкий allowlist мутаций.
- Разделение ответственности: `project-mcp` отдельно от web-процесса, с минимальным набором данных и read-only runtime.
- Лучшая проверяемость ответов `/help`: используются актуальные MCP-данные о Git и составе публичных файлов.

### Ограничения и компромиссы

- Поддерживается только Streamable HTTP; OAuth и stdio-сервера не входят в текущий дизайн.
- `project_files` возвращает максимум 160 путей, поэтому для очень больших репозиториев список может быть усечён.
- Аннотации MCP доверяются как декларации сервера; безопасность мутаций дополнительно удерживается allowlist, но при подключении недоверенных серверов риск остаётся на уровне политики подключения.
- Токены MCP-хранилища (по общей документации проекта) остаются локальной операционной ответственностью; ADR фиксирует архитектуру, но не заменяет процедурный секрет-менеджмент.
