# Автоматическое AI-ревью PR (день 32)

GitHub Action `AI code review` запускается при открытии PR, новом коммите,
повторном открытии и снятии draft. Diff и изменённые файлы читаются из Git;
BM25 находит документацию и связанный код, затем OpenAI возвращает замечания.
Отчёт содержит потенциальные баги, архитектурные проблемы и рекомендации.
Пустые категории остаются пустыми: модель не обязана придумывать замечания.

## Настройка GitHub

1. Добавьте repository Actions secret `OPENAI_API_KEY` через Settings → Secrets
   and variables → Actions. При необходимости задайте variable `OPENAI_MODEL`;
   по умолчанию сохранена модель проекта `gpt-5.3-codex`.
2. После слияния реализации в целевую ветку откройте PR из другой ветки этого
   же репозитория. Fork PR, draft и Dependabot не получают платного ревью.
3. Во вкладке Checks / Actions дождитесь `AI code review`. В Conversation
   появится один комментарий бота с HEAD SHA, замечаниями, цитатами и покрытием.
   После следующего коммита комментарий обновляется. Повторный запуск доступен
   через Actions → Re-run jobs.
4. JSON и Markdown доступны в artifact `ai-review-<PR>-<HEAD>` (14 дней),
   Markdown также выводится в Job summary. API/JSON/валидационные ошибки
   делают job красной, а не превращаются в «замечаний нет».

Первый PR с самим анализатором не может анализироваться ещё отсутствующим
анализатором из `main`: job выводит Bootstrap. До слияния проверка выполняется
на отдельном демонстрационном PR с base `ai-challenge-task-32`. Это настоящий
запуск по событию PR, но не слияние реализации в `main`.

## Контекст и ограничения

Анализатор и его тесты запускаются из **зафиксированного base SHA**, а не из
PR. Полный fetch получает Git-объекты кандидата; checkout, сборка и запуск
кода кандидата не выполняются. Git читается отдельными командами без shell,
external diff/textconv, hooks, replacement objects и наследования ключей.
Actions закреплены по SHA. OpenAI-ключ доступен только шагу генерации.

Это workflow для доверенных участников с write-доступом: они могут менять
workflow в своих ветках. Он не является защищённой песочницей для произвольных
внешних авторов. `pull_request_target` с исполнением кода PR не используется.

Diff строится от merge base до head, поэтому учитывает добавления, изменения,
удаления и переименования. До 24 файлов, 80 000 байт diff суммарно, 128 КиБ
на файл. Файл, который целиком не помещается, пропускается с причиной; текст
не обрезается посреди hunk. Ссылки привязаны к commit SHA. Перед публикацией
ещё раз проверяются открытость PR, head, base и репозиторий автора. Проверка и
запись комментария не атомарны в GitHub; каждый отчёт явно указывает проверенный
HEAD. Предыдущий отчёт не выдаётся за проверку нового коммита.

Корпус RAG — README, `docs/`, другие публичные Markdown, Go, JS/CSS/HTML,
YAML, Dockerfile и go.mod/go.sum **из base**. Из PR никогда не берутся новые
«правила ревью». Скрытые файлы (кроме `.github`), `.env`, пользовательские
данные, `artifacts/`, `tools/`, `vendor/`, старый `documents/` корпус,
символические ссылки, бинарные и сгенерированные файлы исключаются.
Не храните секреты и персональные данные в публичном коде/документации:
allowlist путей не является универсальным детектором секретов.

До 1000 файлов / 12 МиБ корпуса. Chunking по объявлениям Go / заголовкам
Markdown, длинные секции — по 40 физических строк; строки сохраняются точно.
По каждому файлу отдельно ищутся документация и код существующим BM25 из
`internal/projecthelp`, с ограничением до 16 retrieved chunks / 24 000 байт.
В отчёте сохраняются path, section, revision, chunk ID, score и точный текст.

Модель получает нумерованные источники `D*` (строки patch, включая заголовки)
и `R*` (физические строки документа/кода). Замечание должно попадать в реально
добавленную RIGHT или удалённую LEFT строку; диапазон не длиннее 10 строк.
Каждая цитата ограничена 12 строками и восстанавливается из исходного текста.
Неизвестные пути, source ID, диапазоны и неожиданные поля JSON отклоняются.
Каждое замечание должно ссылаться на собственный diff; дополнительно — на
документацию или связанный код, когда они нужны для объяснения.

Prompt отделяет инструкции от недоверенного содержимого, запрещает инструменты
и требует конкретный сценарий, последствие и исправление. Ответ ограничен
8000 output tokens / 8 замечаниями; `store:false`, без истории диалога.
Markdown модели экранируется, внешние картинки/HTML/упоминания не публикуются.
Структурная проверка цитат не гарантирует семантическую правильность ревью.
Модель может ошибаться; решение принимает разработчик. Approval, merge и
исполнение тестов кода PR не входят в этот пайплайн.

## Локальный запуск и Docker

Нужны Go 1.25+, Git и полные SHA, существующие в локальном репозитории:

```sh
go build -o bin/pr-review ./cmd/pr-review
bin/pr-review --base <base-sha> --head <head-sha> --env-file .env --out artifacts/review32/local
```

Без `--publish` GitHub не изменяется. `--collect-only` сохраняет `input.json`
без обращения к модели. Для публикации нужны `--repo owner/repo --pr N
--publish` и `GITHUB_TOKEN` с правом писать комментарии PR.

```sh
docker build --target pr-review -t codex-pr-review:local .
mkdir -p artifacts/review32/docker
docker run --rm --env-file .env \
  -v "$PWD:/repo:ro" -v "$PWD/artifacts/review32/docker:/reports" \
  codex-pr-review:local --base <base-sha> --head <head-sha> --out /reports
```

Контейнер запускается без root; папка отчётов должна быть доступна UID 65532.
Для Git-репозитория другого владельца можно использовать `--user "$(id -u):$(id -g)"`.
Портов и отдельного постоянно работающего сервиса ревью не требуется.

## Проверка

`go test ./...` проверяет настоящий Git diff/RAG, rename/delete, исключение
секретных путей, symlink/generated/large файлы, лимиты, JSON/цитаты, старый HEAD,
обновление только комментария бота и отказ от инструментов модели. API мокается.

Для оплачиваемого прогона на временном клоне текущего HEAD:

```sh
python3 scripts/evaluate-review.py --binary bin/pr-review --env-file .env
```

Пять контролей: ошибка масштаба стоимости (с prompt injection в комментарии),
утечка ключа в `/api/status`, безопасное переименование локальной переменной,
rename/delete и PR из 29 файлов. Проверки ожидаемого пути / отсутствия
замечаний / неполного покрытия узкие: итоговые выводы нужно прочитать.
Код кандидата не запускается. Результаты — JSON/Markdown по каждому сценарию
и `summary.json`; локальные fixture-коммиты не публикуются в GitHub.

Фактический прогон GitHub и демонстрация фиксируются в
`artifacts/review32/REPORT.md` после выполнения.
