# Индексация документов — задание 21

Go-пайплайн: корпус UTF-8 → две стратегии chunking → OpenAI Embeddings → локальный
SQLite → поиск и воспроизводимое сравнение. Веб-вкладка «Документы» показывает
статистику, источники, чанки, результаты поиска рядом и контрольные вопросы.
Генерация ответов чата с найденным контекстом (RAG) в это задание не входит.

## Корпус и объём

`corpus/` — зафиксированный снимок девяти файлов проекта из коммита
`26a6258d890a391e30b398f0ea39917d7e0e5409`:

- README, ARCHITECTURE, MEMORY, PERSONALIZATION, TASK_STATE, INVARIANTS,
  TASK_LIFECYCLE_TEST_REPORT;
- `internal/agent/agent.go` и `internal/memory/workflow.go`.

Исходники сохранены с суффиксом `.go.txt`, чтобы Go не компилировал копии как
пакеты. Загрузчик распознаёт их как Go и разбирает AST. Исходное содержание
сохранено; документы могут отражать прежние версии приложения. В частности,
старое описание MCP в ARCHITECTURE не является спецификацией текущего кода.

Объём: **14 053 слова, 117 498 Unicode-символов**, около **35,1 условной страницы
по 400 слов**. Для кода это эквивалент объёма, не число напечатанных страниц.
Фактические числа, SHA-256 каждого документа и границы разделов проверяются
командой `plan` и сохранены в `../artifacts/docindex/corpus-plan.json`.

Автоматического обхода рабочего каталога нет: индексируется только явно
указанный каталог корпуса. Поддерживаются `.md`, `.txt`, `.go`, `.go.txt`.
Символические ссылки и некорректный UTF-8 отклоняются. PDF нужно предварительно
преобразовать в текст; OCR и импорт PDF не требуются для выбранного корпуса.

## Запуск из корня репозитория

Посмотреть точный объём без ключа, сети и создания индекса:

```sh
go run ./cmd/doc-index plan
```

Построить обе стратегии с настоящими эмбеддингами:

```sh
go run ./cmd/doc-index build -env-file .env
go run ./cmd/doc-index compare -env-file .env
```

`-env-file` необязателен: по умолчанию ключ берётся только из `OPENAI_API_KEY`.
Если указан файл, читаются только `OPENAI_API_KEY` и `OPENAI_BASE_URL`;
существующее окружение имеет приоритет. Shell-подстановки не выполняются.
Ключ не записывается в индекс, отчёт, логи или frontend. Build отправляет тексты
чанков в OpenAI; compare отправляет 20 вопросов. Это платные API-запросы.

Проверить индекс без API и выполнить смысловой поиск:

```sh
go run ./cmd/doc-index inspect
go run ./cmd/doc-index search -env-file .env \
  -query 'Когда задача может перейти в done?' -k 5
```

Для своего корпуса:

```sh
go run ./cmd/doc-index build -env-file .env \
  -corpus ./my-documents -index ./data/my-index.sqlite \
  -size 1800 -overlap 240 -model text-embedding-3-small -dimensions 1536
go run ./cmd/doc-index compare -env-file .env \
  -corpus ./my-documents -index ./data/my-index.sqlite \
  -questions ./my-questions.json -out ./data/my-report
```

Search и compare используют модель и размерность из построенного индекса.
Тексты вопросов и документов кодируются одной моделью. Параметры чата
`OPENAI_MODEL` на эмбеддинги не влияют.

## Две стратегии

**Fixed:** окно 1800 Unicode-символов, перекрытие 240, последний чанк короче.
Границы разделов не учитываются; границы файлов сохраняются.

**Structured:** Markdown разбирается по ATX-заголовкам `#`–`######` с иерархией;
заголовки внутри fenced code blocks игнорируются. Go разбирается через
`go/parser`: комментарии прикрепляются к объявлениям, функции и методы получают
имена. Для обычного текста весь файл считается разделом. Чанк не пересекает
границу раздела. Длинный раздел делится по абзацам в последней половине окна,
при отсутствии границы — по размеру; перекрытие 240 внутри этого раздела.

Единица разбиения — **символы, не токены и не байты**. Точные оплаченные токены
берутся из `usage.total_tokens` API и записываются в отчёт. Максимум 2000 символов
ограничивает вход 8000 байтами UTF-8, консервативно ниже лимита 8192 токена.
Размер API-пакета — до 32 текстов. Используется только текст чанка, без
разного добавления заголовков для разных стратегий.

Для данного корпуса получаются **79 fixed и 143 structured чанка**.

## Метаданные и хранение

`artifacts/docindex/index.sqlite` содержит:

- `document_chunks`: стабильный `chunk_id`, стратегия, источник, заголовок,
  раздел, точный текст, начальная и конечная позиции в Unicode-символах,
  SHA-256 содержимого и нормализованный вектор float32 little-endian;
- `document_index_meta`: версия формата, SHA-256 корпуса, параметры chunking,
  embedding-модель, размерность, время построения, статистика и отчёт;
- `embedding_cache`: проверенные эмбеддинги по модели, размерности и хэшу текста.

Диапазоны `[start, end)` относятся к нормализованному тексту источника:
CRLF заменяется LF, UTF-8 BOM удаляется. Для fixed, пересекающего несколько
разделов, `section` перечисляет их через ` | `.

Нормализация векторов и проверка размерности происходят до записи. Ответ API
может менять порядок: соответствие восстанавливается по `data[].index`.
Пропуски, дубли индексов, другая модель, нулевые или нечисловые векторы отклоняются.
429 и 5xx повторяются до трёх попыток; отмена и тайм-ауты поддерживаются.

Кэш сохраняется после каждого успешного пакета. Полный индекс обеих стратегий
заменяется одной транзакцией только после получения всех векторов. Ошибка
оставляет прежний индекс доступным; повторный build использует кэш.
При успешной перестройке прежний отчёт удаляется: compare нужно запустить заново.
Кэш может содержать тексты в векторном представлении от прошлых сборок; для
полностью нового корпуса можно использовать новый SQLite-файл.

Поиск — точный перебор локальных векторов с косинусным сходством. Для сотен
чанков этого достаточно; FAISS и отдельный векторный сервер не нужны.

## Сравнение

`questions.json` содержит **20 вопросов**, зафиксированных до первого измерения.
Эталон задаётся парой `source` + уникальная `quote` в исходном документе, не ID
чанка. Пример формата:

```json
[
  {
    "id": "example",
    "query": "Когда задача может быть завершена?",
    "relevant": [
      {"source": "TASK_STATE.md", "quote": "Проверка passed относится к текущей версии результата"}
    ]
  }
]
```

Compare проверяет совпадение корпуса с индексом и уникальность цитат, получает
один вектор каждого вопроса и использует его для обеих стратегий. Попадание —
полное включение эталонной цитаты в найденный чанк. Повтор одной цитаты в разных
чанках не увеличивает recall. Сохраняются Hit@5, Recall@5, MRR@5, top-5 для
каждого вопроса, статистика размеров и времени, фактический расход токенов.

Артефакты успешного запуска:

- `artifacts/docindex/index.sqlite` — реальные векторы и все метаданные;
- `artifacts/docindex/comparison.json` — параметры, метрики и полная выдача;
- `artifacts/docindex/comparison.md` — таблицы, результаты по вопросам и выводы.

`corpus-plan.json` — только предварительный анализ, **не готовый индекс и не
отчёт качества**. При недоступном API программа завершается с ошибкой; случайные,
нулевые и mock-векторы не используются как результат задания.

Метрики относятся к этому ручному набору. Альтернативные правильные источники
могут не совпасть с выбранной цитатой; выдача доступна для ручной проверки.
Сравнивается retrieval, а не ответы генеративной модели. Время build включает
сеть и зависит от кэша; structured строится вторым и может использовать кэш
fixed. В отчёте это отмечено, поэтому время не трактуется как чистый benchmark.

## Веб-интерфейс и Docker

Фактический запуск 4 октября 2026 года: 222 вектора по 1536 координат,
90 463 входных токена для корпуса и 517 для контрольных вопросов.
Fixed: Hit@5 **55%**, MRR@5 **0,408**; structured: Hit@5 **70%**, MRR@5 **0,450**.
Это результаты выбранных эталонных цитат, не универсальная оценка моделей.
Полные результаты: [отчёт сравнения](../artifacts/docindex/comparison.md).

После построения запустите приложение обычным способом. По умолчанию оно
открывает `artifacts/docindex/index.sqlite` только для чтения. Для другого
расположения задайте `DOCUMENT_INDEX_PATH`. Если индекса ещё нет, чат работает,
а вкладка показывает инструкцию; после первой сборки перезапустите сервер.

Во вкладке «Документы» просмотр корпуса и готового отчёта не вызывает API.
Каждый новый поисковый вопрос вызывает embeddings API один раз; найденные
фрагменты показываются локально. Содержимое документов выводится как текст.
Все маршруты требуют `X-Codex-Chat: 1` и проверку Origin, как остальные API.

Docker включает CLI `/doc-index`, корпус `/documents/corpus`, вопросы
`/documents/questions.json` и копию артефактов `/documents/artifacts`.
При обновлении поставляемого индекса пересоберите образ. Для отдельной сборки
в постоянный том можно выполнить:

```sh
docker compose run --rm --no-deps --entrypoint /doc-index codex-chat \
  build -corpus /documents/corpus -index /data/documents.sqlite
docker compose run --rm --no-deps --entrypoint /doc-index codex-chat \
  compare -corpus /documents/corpus -questions /documents/questions.json \
  -index /data/documents.sqlite -out /data/docindex-report
```

Чтобы web использовал этот вариант, укажите в Compose
`DOCUMENT_INDEX_PATH: /data/documents.sqlite` вместо встроенной копии.

## Проверки

```sh
go test ./...
go vet ./...
go test -race ./internal/docindex ./internal/web
```

Тесты используют явно обозначенный fake Embedder и локальный HTTP mock;
ключ, сеть OpenAI и реальные платные запросы для них не нужны. Проверяются
Unicode и отсутствие потери текста, стабильность ID, границы Markdown/Go,
перезапуск, кэш, сохранение предыдущего индекса при ошибке, формулы оценки,
валидация ответов API, HTTP-разрешения и ограничение поисковых запросов.

Контракт API: [OpenAI Embeddings](https://developers.openai.com/api/docs/guides/embeddings).
